# Tenable Security Inspector

Portable contract for the shipped Tenable Vulnerability Management and Tenable Security Center scan program, sensor coverage, access control, and vulnerability management assessments.

## Purpose

Tenable Security Inspector gives auditors a read-only view of a Tenable Vulnerability Management tenant and, when configured, a Tenable Security Center console: whether scanning is scheduled, credentialed, and current, whether scanners, agents, and assets cover the estate, who can administer the platform, and whether open findings are prioritized and remediated within their SLA.

## Rationale

Tenable shows each key only what its role may see. An Administrator key gets full user records, while lower roles get the reduced user shape and only the scans, assets, and findings shared with them. A portable implementation must keep that difference visible instead of reading a narrower view as a compliant tenant, so a key that is not confirmed as Administrator never produces a pass on a check that depends on the user list.

Asset and vulnerability data arrive through asynchronous exports whose chunks can fail, be listed beyond the download cap, or carry records with none of the documented members. Each of those conditions marks the export partial and caps the checks built on it, so an export that was only partly read cannot pass.

## Runtime behavior

- The tool only reads, except for the POST requests that start the asset and vulnerability exports.
- Each export is polled every 2 seconds for up to 300 seconds, and only the first max_chunks available chunks are downloaded.
- A throttled or failed request is retried before it counts as failed: HTTP 429 and 5xx answers get up to 4 more attempts, each waiting as long as Retry-After asks up to 30 seconds, and so does a GET that times out or fails before its whole answer arrives. The timeout bounds the wait for the headers and each gap between pieces of the body rather than the whole body, so a large export chunk that keeps arriving is not cut off by it while a body that stalls is retried. Each attempt is capped at 10 minutes, and a body still arriving at the cap is not retried, since another attempt would arrive just as slowly. The POST that starts an export is not sent again after a timeout or a network failure, because Tenable may already have started that export. A request that still fails names its method and path, the status, the timeout, cap, or network error, and the number of attempts, and a chunk that still fails leaves the export truncated.
- Each platform's checks are assessed only when that platform's URL and key pair are configured. Checks for a platform that is not configured are reported as manual and do not change the other platform's results.
- The export job lists cover only the previous 3 days, so the export automation check is a point-in-time signal, and report schedules are not exposed by the API.
- Scanner records are kept without their linking key.

## Non-goals

- Changing Tenable settings, launching scans, or issuing any administrative write request
- Reading report schedules, scan-embedded credentials, or other settings the API does not expose
- Treating a non-Administrator view as complete tenant coverage
- Reproducing a particular programming language, package layout, or command-line framework

## Portable implementation guidance

Keep the API clients, export polling, evidence projection, verdict evaluation, and bundle writer as separable concerns. Count from the full collected arrays at the decision point rather than from evidence previews. Keep each dataset's read state (read, refused, failed, not configured, or partial) next to its records so every finding can say which sources it depended on and why a pass was capped.

## Authentication

Supported modes:

- Tenable Vulnerability Management X-ApiKeys access and secret key pair
- Tenable Security Center x-apikey access and secret key pair

Credential precedence, highest first:

1. Explicit tool arguments
2. TENABLE_* environment variables
3. Tenable YAML config file

Environment variables: `TENABLE_CONFIG_FILE`, `TENABLE_URL`, `TENABLE_BASE_URL`, `TENABLE_ACCESS_KEY`, `TENABLE_SECRET_KEY`, `TENABLE_SC_URL`, `TENABLE_SC_ACCESS_KEY`, `TENABLE_SC_SECRET_KEY`, `TENABLE_TIMEOUT`

Configuration locations: ~/.tenable/config.yaml, Explicit path from config_file or TENABLE_CONFIG_FILE

Credential and deployment variants: Commercial cloud at cloud.tenable.com or a regional *.cloud.tenable.com host, FedRAMP cloud at fedcloud.tenable.com, Tenable Security Center host, alone or alongside a cloud tenant

Configuration fields: `url`, `base_url`, `access_key`, `accessKey`, `secret_key`, `secretKey`, `sc_url`, `sc_access_key`, `sc_secret_key`, `timeout_seconds`

Malformed configuration: Reject malformed or ambiguous configuration before any request; never echo credential values.

## Rate limits

| Scope | Documented limit | Retry headers | Retryable statuses | Policy |
|---|---|---|---|---|
| Tenable Security Inspector | Not published | `Retry-After` | 429, 500-599 | Retry 429 and every 5xx status up to 4 times after the first attempt, and retry a GET that times out or fails before its whole answer arrives the same way, export status polls and chunk downloads included. The timeout (30 seconds by default) bounds the wait for the response headers and each gap between pieces of the body, restarting as each piece arrives, so a body that keeps arriving is not cut off by it and one that sends nothing for that long times out. Each attempt is also capped at 10 minutes, and a request whose body is still arriving at the cap is not sent again, since another attempt would arrive just as slowly. The POST that starts an export is never sent again after a timeout or a network failure, since Tenable may already have started that export; a POST answered with 429 or a 5xx status is sent again like a GET. A Retry-After header in seconds or as an HTTP date measured against the client clock is honored, clamped to 30 seconds (an HTTP date already past waits 250 ms); otherwise wait 500 ms doubled per attempt, capped at 15 seconds. When the retries run out, a POST drew no complete answer, or an attempt reached the cap, the request fails with its method and path, the HTTP status, the timeout, the cap, or the network error, and the number of attempts; a chunk that still fails is a failed download and marks the export truncated. |

### Ordered decision rules

Rules are evaluated from lowest order number to highest. The first matching condition determines the finding status; later rules are not evaluated.

A `matches` condition performs a regular-expression search; anchors are required for whole-value matching, and an `i` flag requests case-insensitive matching. A `ratio` condition divides the numerator by the denominator, applies the declared scale, and rounds to the declared decimal places by choosing the nearest value with exact half cases rounded toward positive infinity; a zero, null, or missing denominator does not match.

## Collection states

| State | Required rendering |

| complete | complete: proven API exhaustion or a successful single-object read. |
| truncated | truncated: preserve seen and total when available plus the exact stop reason. |
| unreadable | unreadable: render data and counts as null and retain a scrubbed error envelope. |

| not configured | not_configured: identify the absent optional feature or credential without treating it as compliant. |

## Integration-specific scrubbing

Shared contract version: 1.1.

Projection stage: Project records to verdict-consumed fields, scrub configured and discovered credentials, then scrub again at every report and archive write sink.

Sensitive fields and values: access_key, secret_key, sc_access_key, sc_secret_key, X-ApiKeys, x-apikey, credentials, key

Credential formats: Tenable Vulnerability Management access and secret key pairs, Tenable Security Center access and secret key pairs

Reviewed benign exceptions: Stable non-secret resource identifiers and public documentation URLs remain visible unless carried in a credential field.

Integration-specific rules:

- Withhold undocumented error bodies; retain only status, media type, byte length, and allowlisted vendor error codes.
- Remove URL user information, queries, and fragments from evidence and reject off-origin pagination links.
- Unavailable counts, arrays, maps, and negative flags are null rather than fabricated empty values.

JSON formatting: UTF-8 JSON with two-space indentation and a trailing newline.

Overwrite policy: Allocate {host}-audit-bundle, or the first of -2 through -50 whose directory and zip are both free, and fail rather than overwrite.

Path safety: Resolve beneath the configured output root and reject traversal, unsafe parents, files, and symbolic-link escapes.

Archive pairing: Write a sibling zip named from the exact allocated bundle-directory path plus .zip.
