# Tenable Security Inspector

Portable contract for Tenable scan, sensor, access-control, and vulnerability-management assessments.

## Purpose

Assess Tenable scan-program, sensor, access-control, and vulnerability-management posture across Vulnerability Management and optional Security Center tenants.

## Design guidance

Keep the two Tenable products as distinct evidence sources. Export completion requires every reported chunk, and a failed poll, missing chunk, unevaluable record, repeated page, or configured cap must remain incomplete rather than becoming an empty result.

## Shared integration contract

This specification requires [shared integration contract version 1.1](./integration-contract.md). The raw contract is available at https://raw.githubusercontent.com/ethanolivertroy/grclanker/main/specs/integration-contract.md.

## Known runtime gaps

- Vulnerability Management and Security Center inventories remain separate sources; a Security Center equivalent adds a suffixed finding and never replaces the cloud control.
- Export status, every available chunk, failed chunks, unevaluable records, configured chunk caps, and poll failures contribute to completeness before any finding count is evaluated.
- A 2xx document missing the endpoint's documented collection member is unreadable rather than an empty inventory.
- Tenable Security Center contributes schedule, scanner, feed, and user equivalents only; cloud-only exports and access-group controls remain manual for Security Center-only tenants.
- TENABLE-07-SC preserves the shipped parent behavior in which a healthy Security Center scanner sample can pass when the scanner inventory is truncated. This partial-pass exception is a report-only runtime candidate; the spec binding does not harden it.
- TENABLE-11 preserves the shipped parent behavior in which a clean permission result can pass when the permissions or user-group inventory is truncated; a broad permission observed in the loaded rows still fails. This partial-pass exception is a report-only runtime candidate; the spec binding does not harden it.
- TENABLE-19 preserves the shipped parent behavior in which external export jobs observed on at least two days can pass when either export-job listing is truncated. This partial-pass exception is a report-only runtime candidate; the spec binding does not harden it.

## Authentication

Supported modes:

- Tenable Vulnerability Management X-ApiKeys access/secret pair
- Tenable Security Center x-apikey access/secret pair

Credential precedence, highest first:

1. Explicit tool arguments
2. TENABLE_* environment variables
3. Explicit or default Tenable YAML/JSON config

Environment variables: `TENABLE_CONFIG_FILE`, `TENABLE_URL`, `TENABLE_BASE_URL`, `TENABLE_ACCESS_KEY`, `TENABLE_SECRET_KEY`, `TENABLE_SC_URL`, `TENABLE_SC_ACCESS_KEY`, `TENABLE_SC_SECRET_KEY`, `TENABLE_TIMEOUT`

Configuration locations: ~/.tenable/config.yaml, Explicit path from config_file or TENABLE_CONFIG_FILE

Credential and deployment variants: cloud.tenable.com, fedcloud.tenable.com, Tenable Security Center URL, Simultaneous VM and Security Center tenants

Configuration fields: `url`, `base_url`, `access_key`, `accessKey`, `secret_key`, `secretKey`, `sc_url`, `sc_access_key`, `sc_secret_key`, `timeout_seconds`

Malformed configuration: Reject malformed or ambiguous configuration before any request; never echo credential values.

## Integration-specific scrubbing

Shared contract version: 1.1.

Projection stage: Project records to verdict-consumed fields, scrub configured and discovered credentials, then scrub again at every report and archive write sink.

Sensitive fields and values: access_key, secret_key, x-apikey, authorization, cookie, password, credentials, username

Credential formats: Tenable X-ApiKeys headers, Security Center x-apikey headers, managed credential payloads, URL user information

Reviewed benign exceptions: Stable non-secret resource identifiers and public documentation URLs remain visible unless carried in a credential field.

Integration-specific rules:

- Withhold undocumented error bodies; retain only status, media type, byte length, and allowlisted vendor error codes.
- Remove URL user information, queries, and fragments from evidence and reject off-origin pagination links.
- Unavailable counts, arrays, maps, and negative flags are null rather than fabricated empty values.
