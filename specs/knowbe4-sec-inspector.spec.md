# KnowBe4 Security Inspector

Portable contract for the shipped KnowBe4 phishing program, training program, user risk, and account governance assessments over the KnowBe4 Reporting API and the optional PhishER GraphQL API.

## Purpose

KnowBe4 Security Inspector gives auditors a read-only view of a KnowBe4 Security Awareness Training account. It covers four areas:

- Phishing program: whether simulated phishing runs often and on a regular schedule, reaches and targets every active user, keeps the phish-prone percentage under its ceiling and falling, and draws reports from the people it tests.
- Training program: whether training campaigns close with high completion, new users enroll within the grace period, users who fail a phishing test receive remedial training, assigned content stays current, and required compliance topics are assigned and completed.
- User risk: whether risk scores stay low and even, every active group sees both phishing and training, and long-standing users show recent activity.
- Account governance: how many people administer the account, whether any of them sit outside its domains, and whether callback (vishing) tests run.

## Rationale

The Reporting API pages by page number and returns no total, Link header, or cursor, so a short page is the only sign that a list has ended. Every walk also stops at a record cap, and reaching it marks the list partial and caps the checks built on it at warn. A fail that rests on something being absent from a partial list, such as a group with no training or a user with no recorded activity, is reported as warn instead.

Recipient-level checks read a sample: by default, the recipient lists of the newest 12 security tests in the window. Coverage and remedial training cannot pass unless the recipients of every test that ran in the lookback window were read in full.

PhishER is a separate product with its own API key. Without the key the tool does not read it, and the report rate check rests on the security test counters alone. With the key, a refused PhishER read caps that check at warn. The Reporting API exposes no SSO or admin MFA settings, no record of report reviews, and no USB drive tests, so those three checks always return manual and name the console evidence a reviewer needs.

## Runtime behavior

- The tool only reads. Every Reporting API request is a GET, and the PhishER requests are GraphQL queries, which change nothing.
- Users stop at user_limit (5000), training enrollments at enrollment_limit (20000), PhishER messages at phisher_message_limit (1000), and every other list, including each sampled test's recipient list, at 20000 records.
- Training campaigns are read 10 per page, other Reporting API lists 500 per page, and PhishER messages 200 per page.
- A refused or failed read never counts as an empty list. A check whose decision needs that read is manual, and a check that uses it only as supporting evidence is capped at warn.
- The account record is cut to its listed fields, and user records lose their comment, custom field, and custom date values before they reach evidence, decision facts, or the bundle. With redact_pii, the export also hashes email and reporter values and masks names, phone numbers, IP addresses, and message subjects.
- The phish-prone baseline is the first three tests that ran, used only once at least four have run, and the trend needs at least four tests in twice the lookback window. Neither count can be configured.

## Non-goals

- Changing KnowBe4 settings, launching or editing campaigns, enrolling users, or issuing any administrative write request
- Judging the content or difficulty of phishing templates and training modules
- Verifying SSO enforcement, report review cadence, or USB drive tests, which the Reporting API does not expose
- Reconciling the KnowBe4 user list against an authoritative directory such as an identity provider or HR system
- Treating a refused read or an unconfigured PhishER key as a compliant result
- Reproducing a particular programming language, package layout, or command-line framework

## Portable implementation guidance

Keep the API client, pagination, recipient sampling, evidence projection, verdict evaluation, and bundle writer as separable concerns. Count from the full collected arrays at the decision point rather than from evidence previews. Keep each dataset's read state (read, refused, not requested, not configured, or partial) next to its records, along with the sampled and unsampled security test IDs, so every finding can say which sources it depended on and why a pass was capped.

## Known runtime gaps

- A Reporting API page counts only its entries that are JSON objects, so a full page of 500 holding an entry that is not a JSON object ends the walk as a last page and leaves the list complete; the records on later pages are never read, and any check can pass on the records that were.

## Authentication

Supported modes:

- Reporting API token: sent as Authorization: Bearer on every KnowBe4 Reporting API read
- Optional PhishER API token: sent as Authorization: Bearer on every PhishER GraphQL request; PhishER is not read without it

Credential precedence, highest first:

1. Explicit tool arguments (api_token, else token, for the Reporting API token)
2. KNOWBE4_* environment variables
3. KnowBe4 YAML config file
4. A base_url or phisher_graphql_url from any source takes precedence over the region's default; with no region, us is used

Environment variables: `KNOWBE4_CONFIG_FILE`, `KNOWBE4_API_TOKEN`, `KNOWBE4_REGION`, `KNOWBE4_BASE_URL`, `KNOWBE4_PHISHER_API_TOKEN`, `KNOWBE4_PHISHER_GRAPHQL_URL`, `KNOWBE4_TIMEOUT`, `KNOWBE4_REDACT_PII`

Configuration locations: ~/.knowbe4-inspector/config.yaml, Explicit path from config_file or KNOWBE4_CONFIG_FILE

Credential and deployment variants: Regions us (the default), eu, ca, uk, and de, matched after trimming and lowercasing; any other region is rejected, Each region's Reporting API host is https://{region}.api.knowbe4.com; its PhishER GraphQL URL is https://training.knowbe4.com/graphql for us and https://{region}.knowbe4.com/graphql otherwise, An explicit base_url or phisher_graphql_url replaces the region's URL, with any user information, query, fragment, and trailing slashes removed

Configuration fields: `api_token`, `region`, `base_url`, `phisher_api_token`, `phisher_graphql_url`, `timeout_seconds`, `redact_pii`

Malformed configuration: Reject malformed or ambiguous configuration before any request; never echo credential values.

Rules are evaluated from lowest order number to highest. The first matching condition determines the finding status; later rules are not evaluated.

A `matches` condition performs a regular-expression search; anchors are required for whole-value matching, and an `i` flag requests case-insensitive matching. A `ratio` condition divides the numerator by the denominator, applies the declared scale, and rounds to the declared decimal places by choosing the nearest value with exact half cases rounded toward positive infinity; a zero, null, or missing denominator does not match.

## Integration-specific scrubbing

Shared contract version: 1.1.

Projection stage: Responses are kept as read, except that the account record is cut to its listed fields with certificate-like fields summarized, and every user, including each recipient's embedded user, loses its comment, custom_field_1, custom_field_2, custom_field_3, custom_field_4, custom_date_1, and custom_date_2. The export writes every core_data dataset through the PII pass when redact_pii is set, which replaces each email, manager_email, reportedBy, reported_by, from, to, or cc value that reads as text with user- followed by the first 12 hexadecimal digits of the SHA-256 of its trimmed, lowercased text and each non-null first_name, last_name, manager_name, phone_number, mobile_phone_number, extension, aliases, employee_number, comment, subject, ip, ip_location, custom_field_1, custom_field_2, custom_field_3, custom_field_4, custom_date_1, or custom_date_2 value with [redacted], and always through the credential pass, which replaces the values of credential-shaped keys with [REDACTED], cuts the values of URL-shaped keys to their scheme and host, and scrubs token-shaped text from every other string. Analysis and compliance files skip both passes.

Sensitive fields and values: api_token, phisher_api_token, Authorization, email, manager_email, reportedBy, reported_by, from, to, cc, first_name, last_name, manager_name, phone_number, mobile_phone_number, extension, aliases, employee_number, comment, subject, ip, ip_location, custom_field_1, custom_field_2, custom_field_3, custom_field_4, custom_date_1, custom_date_2

Credential formats: KnowBe4 Reporting API key, sent as a bearer token, KnowBe4 PhishER Product API key, sent as a bearer token

Reviewed benign exceptions: Stable non-secret resource identifiers and public documentation URLs remain visible unless carried in a credential field.

Integration-specific rules:

- A refused Reporting API or PhishER response is reported with its status line and, when its body is a JSON object, the text of its message, error, and errors[].message fields joined by semicolons, whitespace runs collapsed, credential values scrubbed, and cut to 300 characters; any other body is described by its status line, media type, and byte length and never echoed.
- A 2xx response whose body is not JSON is described by its media type and byte length and never echoed.
- PhishER GraphQL errors are reported as each error's message, else unknown error, joined by semicolons and scrubbed, without the 300-character cut.
- An inventory that was not requested, not readable, or not configured is exported as an explicit marker naming the reason, never as an empty dataset.
