title: Snowflake
description: Read-only Snowflake security posture checks over the SQL REST API with key-pair JWT or OAuth, covering all 25 controls in the Snowflake security inspector spec.
---

The Snowflake integration runs read-only `SHOW` commands and `SNOWFLAKE.ACCOUNT_USAGE` queries through the Snowflake SQL REST API and turns the results into normalized findings with FedRAMP, CMMC, SOC 2, CIS, PCI-DSS, STIG, IRAP, and ISMAP mappings. It never issues `CREATE`, `ALTER`, `DROP`, `GRANT`, or `USE ROLE`; the client rejects any statement that does not start with `SHOW`, `DESCRIBE`, `SELECT`, `WITH`, or `EXPLAIN`.

## What it inspects

- Network policies, account-level activation, and IP allowlist breadth
- MFA coverage for person users, password policies, session policies, SAML2 and SCIM integrations
- Key-pair authentication for `SERVICE`, `SERVICE_AGENT`, and `LEGACY_SERVICE` users
- Role hierarchy, `ACCOUNTADMIN` and `SECURITYADMIN` membership, routine `ACCOUNTADMIN` usage, direct user grants, and `PUBLIC` grants
- Failed login patterns, stale users, retention parameters, `ACCESS_HISTORY` readability, warehouse auto-suspend
- Masking and row access policy assignment, tag-based classification, stage and unload restrictions, Time Travel retention, outbound shares and listings, API and external access integrations
- Tri-Secret Secure and customer-managed keys as manual evidence findings (not queryable through SQL)

## Setup and authentication

The Snowflake SQL REST API accepts key-pair JWTs, OAuth access tokens, and programmatic access tokens. Username and password authentication is not available on the SQL API, so the tools reject password-only configuration with an explicit error.

### Key-pair authentication (recommended)

Generate an RSA key pair and register the public key on the audit user, following the [key-pair authentication guide](https://docs.snowflake.com/en/user-guide/key-pair-auth):

```bash
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub
```

```sql
ALTER USER GRCLANKER_SVC SET RSA_PUBLIC_KEY = 'MIIBIjANBgkqh...';
```

The client builds the JWT with `node:crypto`: `iss` is `<ACCOUNT>.<USER>.SHA256:<public key fingerprint>`, `sub` is `<ACCOUNT>.<USER>` (account and user upper-cased, region and cloud segments stripped from legacy locators), the token is signed with RS256, and it expires within one hour and is refreshed automatically. Encrypted private keys are supported through a passphrase.

### Environment variables

| Variable | Purpose |
|----------|---------|
| `SNOWFLAKE_ACCOUNT` | Account identifier (`orgname-accountname` or legacy locator such as `xy12345.us-east-1`) |
| `SNOWFLAKE_USER` | Audit user |
| `SNOWFLAKE_PRIVATE_KEY_PATH` (or `SNOWFLAKE_PRIVATE_KEY_FILE`) | Path to the PKCS#8 private key |
| `SNOWFLAKE_PRIVATE_KEY` (or `SNOWFLAKE_PRIVATE_KEY_RAW`) | Inline private key PEM (`\n` escapes accepted) |
| `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` (or `PRIVATE_KEY_PASSPHRASE`) | Passphrase for an encrypted key |
| `SNOWFLAKE_TOKEN` (or `SNOWFLAKE_OAUTH_TOKEN`, `SNOWFLAKE_ACCESS_TOKEN`) | OAuth or programmatic access token |
| `SNOWFLAKE_TOKEN_TYPE` (or `SNOWFLAKE_AUTHENTICATOR`) | `KEYPAIR_JWT`, `OAUTH`, or `PROGRAMMATIC_ACCESS_TOKEN` |
| `SNOWFLAKE_ROLE` | Role for every statement (defaults to the user's default role) |
| `SNOWFLAKE_WAREHOUSE` | Warehouse for `ACCOUNT_USAGE` queries (X-Small is enough) |
| `SNOWFLAKE_DATABASE`, `SNOWFLAKE_SCHEMA` | Optional session context |
| `SNOWFLAKE_BASE_URL` (or `SNOWFLAKE_HOST`) | Override for PrivateLink or non-standard hosts |
| `SNOWFLAKE_CONNECTION_NAME` (or `SNOWFLAKE_DEFAULT_CONNECTION_NAME`) | Connection entry to read from the TOML config files |
| `SNOWFLAKE_HOME` | Alternate directory for `connections.toml` and `config.toml` |
| `SNOWFLAKE_TIMEOUT`, `SNOWFLAKE_STATEMENT_TIMEOUT`, `SNOWFLAKE_POLL_INTERVAL_MS` | HTTP timeout (seconds), server-side statement timeout (seconds), and async poll interval |

Precedence is explicit tool arguments, then environment variables, then `~/.snowflake/connections.toml` (a `[<name>]` table) or `~/.snowflake/config.toml` (`default_connection_name` plus `[connections.<name>]` tables), matching the [connections.toml format](https://docs.snowflake.com/en/developer-guide/snowflake-cli/connecting/configure-connections) used by Snowflake CLI and the Python connector. The reader accepts the documented keys `account`, `user`, `role`, `warehouse`, `database`, `schema`, `host`, `private_key_file`, `private_key_raw`, `private_key_file_pwd`, `token`, and `authenticator`.

The TOML reader handles comments, `[table]` headers, and single-line `key = value` pairs (basic, literal, and single-line triple-quoted strings, numbers, and booleans). Any other line, including a multi-line string or a quoted value that does not close on its line, stops the tool with `Unable to parse Snowflake config file: invalid TOML in <path> at line N (INVALID_TOML)`. A missing file is skipped; one that cannot be read stops the tool with `Unable to read Snowflake config file <path> (<errno code>)`. The private key file follows the same rule (`Unable to read Snowflake private key file <path> (<errno code>)`, or `Snowflake private key file was not found: <path> (ENOENT)`), and a key that OpenSSL cannot load is reported as `Unable to load the Snowflake private key (<ERR_ code>)`. None of these messages repeats a line from the file or any key material.

### Recommended read-only role

```sql
CREATE ROLE SNOWFLAKE_AUDITOR;
GRANT IMPORTED PRIVILEGES ON DATABASE SNOWFLAKE TO ROLE SNOWFLAKE_AUDITOR;
GRANT USAGE ON WAREHOUSE AUDIT_WH TO ROLE SNOWFLAKE_AUDITOR;
GRANT ROLE SNOWFLAKE_AUDITOR TO USER GRCLANKER_SVC;
```

`IMPORTED PRIVILEGES` on the `SNOWFLAKE` database unlocks the `ACCOUNT_USAGE` views ([enabling ACCOUNT_USAGE for other roles](https://docs.snowflake.com/en/sql-reference/account-usage#enabling-the-snowflake-database-usage-for-other-roles)). `SHOW` commands only list objects the active role can access, so the tools treat `ACCOUNTADMIN` and `SECURITYADMIN` as full-visibility roles and flag every other role as partial visibility: an empty `SHOW` inventory under a custom role yields `manual` or `warn`, never `pass`. `SHOW SHARES` is stricter: only `ACCOUNTADMIN` lists every outbound share, other roles holding `IMPORT SHARE` list only the shares they own, and roles without the privilege receive an empty result rather than an error, so control 22 passes only under `ACCOUNTADMIN`. `ACCESS_HISTORY` requires Enterprise Edition or higher.

### Statement execution

Statements are submitted with `POST /api/v2/statements?async=true` and polled with `GET /api/v2/statements/{handle}` while the API returns `202`, honoring `Retry-After`. The poll follows the `statementStatusUrl` the API returned only when it is a root path on the configured account origin or an absolute URL that resolves, as a browser would, onto that origin (scheme, host, and port compared after URL normalization, so casing and a default port never matter) and carries no userinfo. Anything else is never requested and the statement fails with `Snowflake SQL API returned a statement status URL that <reason>; the statement was not polled and its result was not read.`, recorded as an `error` outcome with that reason, so the bearer token never leaves for another host: a URL on another origin (`is on origin https://other.example, not the configured account origin https://myorg-myaccount.snowflakecomputing.com`), one carrying userinfo on either origin (`carries userinfo for origin <origin> (configured account origin <origin>)`), a host-moving relative reference such as `@other.example/x`, a protocol-relative (`//host/...`) or backslash (`\\host\...`) form, which resolves to the host it names and is refused as off-origin or, when it names the configured host, as `a protocol-relative or relative reference rather than a root path on the configured account origin <origin> or an absolute URL on it`, a URL on a hostless scheme (`javascript:`, `data:`, `blob:`, `file:`), which is refused by its scheme (`is on origin data:, not the configured account origin <origin>`), a `blob:` URL wrapping the configured origin included, and a URL that `could not be parsed against the configured account origin <origin>`. The request layer refuses the same shapes before any credential is built (`Snowflake SQL API request refused: the request URL <reason>, so no request was sent.`). Every refusal is fixed text naming only the configured origin and the rejected origin: no path, query, fragment, or userinfo of the returned URL reaches any text. The response that completes the statement carries partition 0 in its `data`; when `resultSetMetaData.partitionInfo` lists more than one partition, each additional partition (1 through the last, within `max_partitions`) is fetched with `GET /api/v2/statements/{handle}?partition=N`. `429` and `5xx` responses are retried with exponential backoff, HTTP timeouts abort the request, and error messages are scrubbed as described under Export bundle.

Every statement outcome carries `status` (`ok`, `denied`, `error`, `timeout`, or `not_requested`) and, only when `ok`, `numRows`, `partitionCount`, `fetchedPartitions`, and `truncated`; a statement that did not complete has all four set to `null` rather than `0` or `false`. `not_requested` is the outcome of a statement that was never sent because no bearer token could be built: a private key that does not load (a malformed PEM body, an encrypted key with the wrong passphrase) or a missing token. Its error reads `Not requested: the Snowflake private key could not be loaded (<code>); no statement was sent.` with OpenSSL's `ERR_OSSL_*` code (or `INVALID_PRIVATE_KEY`), the failure is not retried, and no endpoint, HTTP status, or statement text is recorded for it. Truncation is recorded on three exits: the partition cap (`max_partitions`, default 50) leaves `fetchedPartitions` below `partitionCount`; an `ACCOUNT_USAGE` query whose rows reach `row_limit` (default 20,000) is truncated; and the six `SHOW` inventories (`SHOW NETWORK POLICIES`, `SHOW INTEGRATIONS`, `SHOW WAREHOUSES`, `SHOW DATABASES`, `SHOW SHARES`, `SHOW REPLICATION GROUPS`) are collected with a 10,000-row cap because Snowflake returns at most 10,000 rows from a `SHOW` command and reports no total, so a full page is recorded as truncated. A finding that reads a truncated statement gains `Partial inventory: <key> hit the N-row limit (M rows seen)` or `<key> returned F/P partitions (R/N rows seen)` in its summary and `evidence.partial_inventory`; a `pass` drops to `warn` and other verdicts keep their status.

### Export bundle

`core_data/<statement key>.json` and the `statements` array echoed by each assess tool are the same snapshot per statement: `{ key, statement, status, columns, rows, numRows, partitionCount, fetchedPartitions, truncated, rowLimit, error }`. A readable statement carries its result set as returned (`rows: []` and `numRows: 0` when it matched nothing). A statement that was denied, failed, or timed out carries `columns: null`, `numRows`, `partitionCount`, `fetchedPartitions`, and `truncated` as `null`, and in place of `rows` a marker object `{ collected: false, status, statement, error }` naming the statement that was actually executed and its scrubbed error, so a denial is never mistaken for an empty result. A statement that was never sent (`not_requested`) has `statement: null` on the snapshot and in the marker, plus `code` with the local failure code, because the bundle names only statements the run executed. `core_data/access_check.json` lists every probed surface with `status` (`readable`, `denied`, `error`, `timeout`, `not_requested`), `statement` (`null` when never sent), `rowCount` (`null` unless readable), and the error; its `authentication` field and `authenticationNote` say whether the run observed its own identity: `confirmed` (`Authenticated as <user> with role <role>.` from the session context row), `unconfirmed` (statements were sent but the session context did not complete, so the configured user and role are reported as configured, not as observed), or `not_authenticated` (`Not authenticated: the Snowflake private key could not be loaded (<code>); no request was sent.`, with `user: null` and no role). `compliance/executive_summary.md` and `metadata.json` carry the same statement, and `metadata.json` counts `requested_statement_count` and `not_requested_statement_count` beside `statement_count` and `failed_statement_count`. `_errors.log` lists `[status] key: error` followed by the statement text for every statement that did not complete; a `not_requested` line has no statement text.

Error text follows its own rule, applied when an API error is constructed and again wherever an error string is recorded (statement markers, `_errors.log`, finding evidence, the access check, and tool error payloads). A value inside a carrier is removed whatever its shape: the value of a credential-named header (`Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, and similar), a cookie or session assignment, URL userinfo and query pairs (the query string collapses to `?[REDACTED]`), the value after a scheme word (`Bearer`, `Basic`, `Digest`, `Token`, `OAuth`, `Negotiate`, `NTLM`, `SSWS`, `ApiKey`, `Splunk`, `Snowflake`, and `HMAC`, in any casing; the scheme word stays), and the value of every credential-named `key=value` or `key: value` pair. The credential-named pair is read before any scheme word: a key that names a credential loses its value whatever word it starts with, so `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE=Snowflake rejected` renders `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE=[REDACTED] rejected`, `sslPassword=splunk rejected` renders `sslPassword=[REDACTED] rejected`, and `db_password: token` renders `db_password: [REDACTED]`. A scheme word acts under an Authorization-style key (`Authorization`, `Proxy-Authorization`, `WWW-Authenticate`), where the run after it goes whatever its shape or the scheme's casing (`Authorization: Snowflake <token>` renders `Authorization: Snowflake [REDACTED]`, `Authorization: sNoWfLaKe <token>` renders `Authorization: sNoWfLaKe [REDACTED]`, `Authorization: SSWS prod-us-east-2026` renders `Authorization: SSWS [REDACTED]`) while a pair list after the scheme, under a request header or a challenge, is read pair by pair as described below (`WWW-Authenticate: Bearer realm="api"` stays), and bare in prose, where the word after it is ordinary text when it is a mechanism word (`authentication`, `credentials`, `challenge`), a version (`OAuth 2.0`), an auth-param (`realm="api"`), or one plain word after a lowercase spelling or a product name (`Basic authentication failed`, `the bearer presented an expired token`, `Splunk Enterprise rejected the request`, and `Snowflake statement failed` stay), while a header-cased pure scheme followed by a run of 8 or more characters loses the run whatever its shape (`Bearer abcdefghijkl rejected` renders `Bearer [REDACTED] rejected`, `replayed BASIC <token> upstream` renders `replayed BASIC [REDACTED] upstream`). The pair rule holds whatever the value's shape and length and wherever the pair sits, in the `=`, `: `, `:`, and JSON forms, in prose and inside a JSON string alike (`upstream echoed DB_PASSWORD: monkey while proxying` renders `DB_PASSWORD: [REDACTED] while proxying`, and `InvalidAuthenticationToken: Access token has expired` renders `InvalidAuthenticationToken: [REDACTED] token has expired`); a credential word anywhere in the key makes it a pair key (`DB_PASSWORD`, `SPLUNK_PASSWORD`, `OKTA_CLIENT_TOKEN`). Three key classes refine that, tested in this order: a key ending in `secret_id`, `session_id`, or `token_id` in any prefix, casing, or separator (`VAULT_SECRET_ID`, `role_secret_id`, `token_id`, `tokenId`) or naming a session id (`sid`, `jsessionid`) carries a bearer credential and loses its value whatever the shape, a UUID included; a URL-valued webhook key (the bare word `webhook` or `hook`, or a `webhook*`, `*hook_*`, or `callback_*` key whose final segment is `url`, `uri`, or `endpoint`) keeps its origin and loses its path and query, while a webhook key that is not URL-valued follows the rule for its own final segment (`webhook_count=3` stays, `webhook_secret=<value>` goes whole); and a credential-named key whose final segment is `url`, `uri`, `endpoint`, `method`, `algorithm`, `audience`, `issuer`, `shape`, `type`, `mode`, `path`, `file`, `dir`, `limit`, `count`, `id`, `name`, `policy`, `policies`, `ttl`, `uses`, `cidrs`, or `accessor` names a setting (`token_endpoint`, `auth_method`, `token_type`, `api_key_id`, `access_key_id`, `key_id`, `private_key_id`, `secret_name`, `secret_id_ttl`, `token_max_ttl`, `secret_id_num_uses`, `token_bound_cidrs`, `secret_id_accessor`) and keeps a value that is neither token-shaped nor a configured secret (`secret_id_ttl=3600`, `key_id=kid-primary`, and `secret_name=db-credentials-prod` stay; `token_type=<token>` goes). A key without a credential word (`OKTA_CLIENT_ID`, `client_id`, `tenant_id`, `SUMO_ACCESS_ID`, `SNOWFLAKE_ACCOUNT`, `X-Request-Id`) is an identifier rather than a pair key, so its value is judged by shape alone. A credential-named command-line flag is a pair too, with a space or `=` before its value (`psql --password <value> -h db` renders `psql --password [REDACTED] -h db`, `helm --set db.password=<value> upgrade` renders `helm --set db.password=[REDACTED] upgrade`, `-Dspring.datasource.password=<value>` renders `-Dspring.datasource.password=[REDACTED]`). A quoted value in any of these carriers (plain, single, or JSON-escaped quotes, as in `Cookie: sid="..."`, `Authorization: Bearer "..."`, or `\"Authorization\": \"Bearer ...\"`) is removed with its quotes kept, and a quote alone never makes a header value a credential (`Content-Type: "application/json"` stays). On a compound header line the reader is quote-aware at every JSON depth: a quoted value ends at the closing quote that matches its opener (the same quote character behind the same run of backslashes), so an escaped inner quote is inner content and goes with the value (`{"Cookie": "sid=\"...\""}` renders `{"Cookie": "[REDACTED]"}` and `{"X-Api-Key": "\"...\""}` renders `{"X-Api-Key": "[REDACTED]"}`, at the top level and inside a double-escaped raw JSON string alike); a quoted value that opens with a scheme word keeps the scheme and loses the rest (`{"Authorization": "Bearer \"...\""}` renders `{"Authorization": "Bearer [REDACTED]"}`), except that a scheme followed by a pair list is read pair by pair, under `Authorization`, `Proxy-Authorization`, and `WWW-Authenticate` alike: a quoted value in the list is the credential and goes whatever its key, unless the key is a descriptive parameter (`realm`, `qop`, `algorithm`, `charset`, `error`, `error_description`, `error_uri`, `scope`), and a bare value follows its key's own rule, so `Authorization: Snowflake Token="<token>"` renders `Authorization: Snowflake Token="[REDACTED]"`, any other `<Scheme> <Key>="..."` pair renders the same way (`Authorization: Bearer blob="<token>"` renders `Authorization: Bearer blob="[REDACTED]"`), a Digest header keeps `realm="api"`, `qop=auth`, and `nc=00000001` and loses `username`, `nonce`, `uri`, `cnonce`, `response`, and `opaque`, a challenge's `WWW-Authenticate: Bearer realm="api", error="invalid_token"` stays whole, and `"VERACODE-HMAC-SHA-256 id=...,ts=...,nonce=...,sig=..."` renders `"VERACODE-HMAC-SHA-256 [REDACTED],ts=...,nonce=[REDACTED],sig=[REDACTED]"` (an unquoted first run after the scheme goes whole, and the pairs after it follow their keys). The same list rule reads a pair list after a scheme word in prose, bare, JSON-escaped, and inside a JSON string alike (`upstream said Bearer blob="<token>"` renders `upstream said Bearer blob="[REDACTED]"`, and `{"headers":{"Authorization":"Snowflake Token=\"<token>\""}}` renders `{"headers":{"Authorization":"Snowflake Token=\"[REDACTED]\""}}`). An unquoted cookie or header value ends at a `;` or `,` before the next `Name:` token (or at the end of the line), and an unterminated quote ends the same way rather than swallowing the following header, so that header keeps its name and gets its own carrier treatment: `Cookie: sid=...; X-Api-Key: ...; Content-Type: application/json` renders `Cookie: [REDACTED]; X-Api-Key: [REDACTED]; Content-Type: application/json`, and `Cookie: sid="...; X-Api-Key: "..."; Content-Type: "application/json"` renders `Cookie: [REDACTED]; X-Api-Key: "[REDACTED]"; Content-Type: "application/json"`. A `;` inside a URL query value is part of the value (URLSearchParams semantics), so a relative `/api/v1/things?token=hunter2;restofsecret` renders `/api/v1/things?token=[REDACTED]` with no tail and an absolute URL's query collapses to `?[REDACTED]` as before, in the plain, JSON-escaped, and slash-escaped spellings alike; the `;` separator belongs to `Cookie` and `Set-Cookie` parsing alone, and the cookie reader runs before the query pass, so `Cookie: &sid=a; pref=b` still renders `Cookie: [REDACTED]`. An apostrophe is a cookie character, so `Cookie: sid=O'<value>; X-Api-Key: <value>` renders `Cookie: [REDACTED]; X-Api-Key: [REDACTED]` and `Cookie: theme=dark; my'pref=<value>` renders `Cookie: [REDACTED]`. The next header's name may carry any RFC 7230 token character, so a dotted or underscored name (`X.Api.Key:`, `X_Api_Key:`) is recognised as the next header and its value is judged by its own key. A literal JSON escape (`\n`, `\r`, `\t`, `\b`, `\f`, `\/`, `\uXXXX`: the two- or six-character sequence as it sits inside a JSON string, not the control character) is a boundary before every carrier opener: a header name, scheme word, pair key, URL, or token that begins right after one is read on its own and never as the value of the word before the escape, so `request headers:\u000aAuthorization: Splunk <key>` renders `request headers:\u000aAuthorization: Splunk [REDACTED]` and `proxy:\tpassword: hunter2` renders `proxy:\tpassword: [REDACTED]`; the escape sequence itself stays, a token glued to an escape never takes the escape letter as its first character, a value, URL, or query pair ends at the backslash that opens the next escape, and a `\/` escape is a boundary rather than a path separator, so a key or token after it is judged on its own. A URL whose slashes are JSON-escaped (`https:\/\/hooks.example.com\/a?token=<value>`) is still read as a URL, so its userinfo and query go the same way (`note https:\/\/hooks.example.com\/a?[REDACTED] next`). The userinfo of a URL ends at the first `/`, `?`, or `#`, so an `@` inside a query or fragment never turns the query into the host: `https://h?e=a@x.com&token=s3cr3t` renders `https://h?[REDACTED]` and `https://h#f@x.com` renders `https://h#[REDACTED]`, in the plain and the slash-escaped spelling alike, and a bare `?` or `#` left before an earlier marker stays as it is, so a second pass adds no second marker. A configured secret (the bearer token, the JWT built from the key pair, the private key, and its passphrase) is removed whatever its shape, in its raw, JSON-escaped, URL-encoded, base64, and base64url forms. A value with a real token shape is removed bare: PEM blocks, JWTs, AWS key IDs and secrets, other vendor-prefixed tokens, hex digests of 32 or more characters, and runs of 16 or more characters that carry a base64 symbol, more than one digit group, or token casing. A bare value shaped like a name (words joined by hyphens or underscores with at most one digit group, such as `prod-us-east-2026`, or a camelCase identifier whose words average three or more letters, such as `resultSetMetaData`, `statementHandle`) is indistinguishable from a resource name and stays, and so does a token-shaped segment of a bare request path or file path (`/api/v2/statements/<handle>`, the `config.toml` path), so the endpoint or file an error names is the one the run used; inside a URL with a scheme every path segment keeps the rule. The last segment of a bare path used as a label (`/home/auditor/.snowflake/rsa_key.p8: <detail>`, `/oauth/token-request: invalid_client`, `/api/v1/api-tokens: request failed with 403`) is a request target rather than a pair key, so the text after it stays, unless that segment itself names a credential (it ends in `password`, `passwd`, `passphrase`, `pwd`, `secret`, `token`, or `key`, or is a bearer id) and the value stands alone on the line, in which case the label is a pair (`kv/password: <value>` renders `kv/password: [REDACTED]`); inside a URL with a scheme the pair rule still applies. Data written to the bundle follows the data-side rule: every string leaf of a `core_data/` snapshot, an assess payload, and the access check passes through the same carrier and shape rules with the generic long-run and hex-digest rules left off, so a vendor-prefixed token (`sk_live_`, `xox*-`, `ghp_`, `AKIA`, and the rest of the vendor set), a JWT, a PEM block, or a credential carrier inside a free-text field (a policy comment, a user comment, a share comment) is removed there too (`key sk_live_<24 characters> end` renders `key [REDACTED] end`), while an identifier such as `prod-us-east-2026-cluster` or a bare random run survives as evidence.

## Verdict semantics

Every finding carries `id`, `control`, `title`, `severity`, `status`, `summary`, `evidence`, and `mappings`. Statuses follow these rules:

- `pass`: the enabling flag was read and satisfied on a complete inventory from a role with sufficient visibility.
- `warn`: the control is partly met, or the evidence is partial (truncated partitions, row limit hit, custom role without full `SHOW` visibility, items with missing dates).
- `fail`: the control is not met, including empty inventories where emptiness contradicts the control's intent (zero network policies, zero password policies, zero masking policies).
- `manual`: a required statement was denied, failed, or timed out; the control is not verifiable through SQL; the account edition does not expose it; or the empty result cannot be distinguished from view latency or restricted privileges. The summary names the cause and the evidence to collect.

Items with a NULL `LAST_SUCCESS_LOGIN` are reported in their own bucket and never counted as active. An empty result only passes when the control's intent makes emptiness compliant and the statement was readable: no direct user grants (10), no `PUBLIC` grants (16), no outbound shares (22, only under `ACCOUNTADMIN`), and no enabled API or external access integrations (23, only under `ACCOUNTADMIN` or `SECURITYADMIN`).

Two further rules apply to every finding:

- A finding that also reads an optional statement (the session context for 19, 22, 23, and 24, `ACCESS_HISTORY` for 13, `TAG_REFERENCES` for 14, `SHOW REPLICATION GROUPS` for 22) never passes while that statement is denied, failed, or timed out. The summary appends `Unreadable inventory: <key> was denied (insufficient privileges): <error>, so <what went unchecked>` and `evidence.unreadable_inventories` names the key; the pass drops to `warn`, or to `manual` for control 22 when the session context cannot verify the role as `ACCOUNTADMIN`. Other verdicts keep their status and gain `Unreadable inventory: <key> (<status>)`.
- Every statement text, HTTP status, and endpoint named in a summary, in `evidence.statements`, in the access check, or in `_errors.log` comes from a request the run actually made; the outcome status (`denied`, `error`, `timeout`) is classified from the observed error or HTTP status, and a statement that was never sent is recorded as `not_requested` under its key with `statement: null`, so `POST /api/v2/statements` and the statement text appear nowhere for it. When no request was sent the run does not claim an identity: the access check, the executive summary, and `metadata.json` report `not_authenticated` with the key failure code, the assessment `summary.role` renders `null`, and no visibility note is derived from the configured role. Row counts derived from a statement that did not complete render `null` in evidence and in the assessment `summary`, never `0`. A count judged over a statement that completed with unfetched partitions or a hit row limit renders `null` too, never the count of the rows read, with the seen-of-total beside it in `evidence.statements[].rows`, `evidence.partial_inventory`, and the summary's `Partial inventory: <key> returned F/P partitions (S/N rows seen)`: `enabled_human_users`, `password_human_users`, `users_with_unknown_mfa_flags`, `service_users`, `users_without_login_timestamp_count`, and every `user_classes` count (3, 5, 12) while the `users` read was partial, and `successful_logins` and `failed_logins` (11) while the `login_outcomes` read was partial; the population words in those summaries carry `among the rows read`. An empty class that came from a partial read is unread rather than absent: control 5 renders `manual` with `No user typed SERVICE, SERVICE_AGENT, or LEGACY_SERVICE was among the N user rows read, and the read stopped early, so the service account inventory is unread rather than empty` instead of `None of the N users are typed ...`, and control 11 renders `manual` with `No LOGIN_HISTORY outcome row for the last N days was among the rows read, and the read stopped early, so the login window is unread rather than empty` instead of the empty-window note. A complete read keeps its real zeros and its wording.

## Limitations and manual controls

- Tri-Secret Secure (20) and customer-managed keys (21) are never SQL-verifiable and always require Snowflake Support and cloud KMS evidence.
- `ACCOUNT_USAGE` views lag: `USERS` and grants up to 2 hours, `LOGIN_HISTORY` up to 2 hours, `QUERY_HISTORY` up to 45 minutes, `ACCESS_HISTORY` up to 3 hours. Recent changes may not be visible, which is why empty inventories become `manual` rather than `pass`.
- `SHOW` commands are role-scoped. Use `ACCOUNTADMIN` or `SECURITYADMIN` for complete inventories; otherwise controls 1, 6, 19, 22, 23, and 24 cap at `warn` or `manual`.
- Password authentication and browser-based SSO are not supported by the SQL REST API.
- Replication and failover groups are collected as evidence for control 22 but Standard Edition accounts return an empty inventory; Trust Center findings are not queried in this release.
- Inventory queries carry a `row_limit` (default 20,000) and a partition cap (50), and `SHOW` commands a fixed 10,000-row cap; hitting any of them marks the statement truncated and downgrades any `pass`, and a finding that reads several statements never passes while one of them is unreadable (the summary names the statement).
