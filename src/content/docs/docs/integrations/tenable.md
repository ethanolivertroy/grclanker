---

The Tenable inspector audits a Tenable Vulnerability Management tenant (cloud.tenable.com or the FedRAMP cloud fedcloud.tenable.com) and, optionally, a Tenable Security Center deployment. It is read-only: the only POST calls are the documented asset and vulnerability export requests, and no scan, user, policy, or exclusion is ever modified.

## What it inspects

- Scan program: scan templates in use, recurring schedule discipline, credentialed scan ratio, scan exclusions, compliance audit templates, and legacy target groups.
- Sensors and assets: asset discovery coverage, Nessus Agent deployment and grouping, linked scanner health, plugin currency, network objects, and asset tagging.
- Access control: user roles and role counts, MFA and SAML enforcement, API key usage, permissions and legacy access groups, managed credential hygiene, and the activity log.
- Vulnerability management: VPR prioritization coverage, severity SLA backlog and mean time to remediate, and export automation evidence, all driven by the bulk vulnerability and asset exports.
- Tenable Security Center equivalents for scan schedules, scanner health and plugin feeds, and user hygiene, when a Security Center URL is configured.

## Setup and authentication

### Tenable Vulnerability Management

1. Sign in to Tenable Vulnerability Management as a user with the Administrator [64] role. Lower roles work but produce partial views: Scan Manager keys only see their own or shared scans, and any key below Administrator receives a reduced `GET /users` payload, so the inspector caps verdicts at warn and says so in the summary.
2. Generate an API key pair from Settings > My Account > API Keys.
3. Export the keys: set `TENABLE_ACCESS_KEY` and `TENABLE_SECRET_KEY` in the environment from your secrets manager (their values are never shown here), and optionally the platform URL:

```bash
export TENABLE_URL="https://cloud.tenable.com"      # default; use https://fedcloud.tenable.com for FedRAMP
```

Requests carry the documented `X-ApiKeys` header, whose two named parts (`accessKey` and `secretKey`) hold the access key and the secret key. Keys are never written to disk. Every error string passes through one redacting sink before it reaches a finding, a tool result, or a bundle file, and a non-JSON error body (an HTML 502 page, a WAF block, an SSO interstitial) is never echoed; the message records only the status and the body length, for example `403; non-JSON text/html response body (1204 bytes, not echoed)`. JSON error bodies contribute their documented `error`, `error.message`, `message`, or `error_msg` fields only, scrubbed before they are shortened so a cut can never leave the head of a secret behind.

A 2xx answer that is not the documented JSON document is an unreadable surface, never an empty inventory (the silent-success class). A Vulnerability Management or Security Center 200 with an empty body, the HTML page a proxy or SSO portal serves in place of the API, a foreign JSON value, or a JSON object without the documented member (`scans`, `users`, `scanners`, `response`, and so on) is described by status, media type, and size only, for example `200 OK with a JSON response body without the documented "scans" array (2 bytes, not echoed)`, and recorded with the observed status as a surface that was not read: the access probe is not readable, the dataset carries the not-collected marker, and the findings that depend on it render manual or capped, never pass on a missing list.

The scrub draws one boundary. A value inside a carrier is replaced with `[REDACTED]` whatever its shape: `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Cookie`, `X-ApiKeys`, `x-apikey`, `X-SecurityCenter`, and similar header lines, where a quoted value (in double, single, or JSON-escaped quotes) ends at its closing quote and goes with its quotes whatever the name of the cookie or key pair that carries it, even when a `; Name:` sits inside the quotes, and an unquoted value ends at the `;` or `,` before the name of the next header on a compound line (several headers separated by `;` or `,`) or else at the end of the line, so cookie attributes such as `Path` and `Expires` go with the cookie, a quoted value that nothing closes ends as an unquoted one does, the next header keeps its name and gets its own treatment, and a `Content-Type` or `Date` after a cookie keeps its name and value; quotes escaped to any depth (`\"` one level down, `\\\"` two) are read at their own depth, so a header pair, credential pair, quoted attribute, or quoted assignment inside a JSON body that was stringified into a string value loses its value and keeps its escaped quotes; cookie and session assignments; the user-and-secret prefix before the host in a URL; the URL query parameters named `token`, `api_key`, `secret`, and `pass`; the values after the schemes `Bearer`, `Basic`, `Token`, and `ApiKey`; credential-named assignment pairs in their three spellings (equals sign, colon, and quoted JSON member) and XML attributes (`password`, `secret`, `token`, `api_key`, `access_key`, `secret_key`, `private_key`, `client_secret`, `registration_code`, `linking_key`, `session_id`, and their camelCase forms). A configured secret (each half of the `X-ApiKeys` and `x-apikey` pairs, four characters or longer) is replaced wherever it appears, whatever its shape, in its base64, base64url, URL-encoded, and JSON-escaped forms too. Real token shapes go even when bare in prose: runs of sixteen or more characters with base64 symbols, scattered digits, or token casing, hex digests, JWTs, AWS access key ids, and PEM blocks. A bare value shaped like a name (words joined by hyphens or underscores with at most one numeric segment, such as `prod-us-east-2026` or `sc-scanner-01`) standing alone in prose is indistinguishable from a resource name and stays, as do template titles such as `Basic Network Scan`, count fields such as `"api_keys": 2`, and this integration's own vocabulary (`credential_threshold`, `status_code`, `plugin_set`). The module's own fixed text is worded to cross that boundary intact: an `_errors.log` line reads `credentials dataset: <error>`, never `credentials: <error>`, which the pair rule would read as a credential and replace, and the access check says `credentials requires role Basic with Can Use on credentials; <cause>` rather than `needs the Basic role:`, since Basic is a Tenable role name as well as an authentication scheme. The test suite drives every fixed text the module emits on refused, unavailable, failed, capped, and silent-success paths through the scrub and requires it back unchanged.

### Tenable Security Center (optional)

Security Center controls run when a Security Center URL is configured. Set `TENABLE_URL` to the Security Center host to inspect only Security Center, or set `TENABLE_SC_URL` alongside the cloud variables to inspect both.

```bash
export TENABLE_SC_URL="https://securitycenter.example.internal"
```

Set `TENABLE_SC_ACCESS_KEY` and `TENABLE_SC_SECRET_KEY` in the environment the same way. Requests use the documented `x-apikey` header, whose two named parts (`accesskey` and `secretkey`) hold the access key and the secret key, against `/rest/` resources. API keys must be enabled in Security Center (System > Configuration > Security) and generated per user. Session token authentication (`POST /rest/token`) requires a write call to log in and is not implemented; use API keys.

### Configuration file

Values not supplied as tool arguments or environment variables are read from a YAML or JSON file at `TENABLE_CONFIG_FILE` or `~/.tenable/config.yaml`:

```yaml
access_key: "..."
secret_key: "..."
url: "https://cloud.tenable.com"
sc_url: "https://securitycenter.example.internal"
sc_access_key: "..."
sc_secret_key: "..."
```

Precedence is explicit tool arguments, then environment variables, then the config file.

A file named explicitly (the `config_file` argument or `TENABLE_CONFIG_FILE`) must be readable and parse; the default path is skipped silently when absent, and an empty file contributes no settings. Loader errors use fixed text and never quote the file: a read failure reports `Unable to read Tenable config file <path> (<CODE>)` with only the errno code (`ENOENT`, `EACCES`, `EISDIR`), a parse failure reports `Unable to parse Tenable config file: invalid YAML in <path> at line N (INVALID_YAML)` with the line taken only from the parser's structured position (omitted when the parser throws something else, such as the plain error an unresolved alias `key: *value` produces), and a file that is not a mapping reports `INVALID_CONFIG_SHAPE`. Neither the filesystem message nor the parser message (which quotes the offending source line, or the alias value itself) is ever interpolated, so a misplaced key in a malformed file cannot leak through the error.

## Tools

| Tool | Purpose |
|------|---------|
| `tenable_check_access` | Probes every read surface the assessments depend on (scans, templates, export job lists, scanners, agents, networks, exclusions, credentials, users, groups, roles, permissions, audit log, tags, target groups, and Security Center current user, scans, scanners, users), reports whether the key holds the Administrator role, and names the role each refused surface needs. |
| `tenable_assess_scan_program` | Spec controls 1, 2, 4, 13, 17, 20 plus the Security Center schedule equivalent. |
| `tenable_assess_sensor_coverage` | Spec controls 3, 5, 6, 7, 8, 9, 16 plus the Security Center scanner equivalent. |
| `tenable_assess_access_control` | Spec controls 10, 11, 12, 18 plus the Security Center user equivalent. |
| `tenable_assess_vulnerability_management` | Spec controls 14, 15, 19 using the bulk vulnerability and asset exports. |
| `tenable_export_audit_bundle` | Runs everything above and writes `core_data/` (API snapshots with credential-bearing values redacted, see below), `analysis/` (findings.json and per-category summaries), `compliance/` (executive summary, unified matrix, one report per framework), `QUICK_REFERENCE.md`, `_errors.log` when collection partially failed, and a `.zip` paired with the allocated output directory (a rerun never overwrites a prior bundle). |

`core_data/` is not a verbatim dump. `policy_details.json` keeps only `uuid`, `name`, `settings`, and `plugins` from `GET /policies/{policy_id}`; the `credentials`, `audits`, and `scap` blocks are dropped before storage. `scanners.json` replaces each scanner's `key` (linking key), `registration_code`, and `license` block with `[REDACTED]`. Every collected dataset then passes through a property-name redaction that replaces the value of any property whose name denotes a credential (`password`, `secret`, `token`, `api_key`, `access_key`, `secret_key`, `private_key`, `client_secret`, `registration_code`, `authorization`, `cookie`, session ids, and their camelCase forms), the `value` of `{name, value}` pairs whose `name` matches (activity log `fields`, for example), and every carrier embedded in a string value (the header, cookie, scheme, query, userinfo, credential-pair, and private PEM rules of the boundary above; a public certificate and an opaque identifier stay, because in evidence they are not secrets). A bare `key` property is not redacted: Tenable tags are `{key, value}` pairs and the tag key is evidence. The same redacted objects feed the findings and tool results, so nothing the assessments return can carry a value the bundle would not. Finally, every bundle file and every tool result passes through the configured-secret pass on its way out: each string is checked for the configured keys in every encoded form, so a key echoed by an upstream body cannot survive even where the general scrub would have left evidence alone.

A dataset that was refused, failed, or never requested is never written as an empty list or `null`. Its `core_data/` file holds a marker in its place, `{ "collected": false, "status": <observed HTTP status or null>, "dataset_status": "forbidden" | "error" | "not_configured", "endpoint": "GET /...", "error": "<scrubbed message>" }`, and the finding that depends on it carries the same `collected: false`, `endpoint`, and `http_status` fields. Every assessment summary carries a `collection` object with one entry per dataset it read (`status`, `endpoint`, `http_status`, `seen`, `total`, `truncated`, `error`); `truncated` is derived from the observed page walk (records seen against `pagination.total`, a page cap reached while pages were still full, or a replayed page), never from a default, and `seen`, `total`, and `truncated` render `null` for a dataset that was not read. Every endpoint or status code named anywhere in a finding, summary, tool result, or `_errors.log` line is the request that was actually made and the status it actually returned; a platform that is not configured names no endpoint, because no request was sent.

Every assessment accepts the shared authentication arguments plus thresholds such as `stale_scan_days` (30), `stale_asset_days` (30), `agent_offline_days` (7), `plugin_stale_hours` (24), `inactive_user_days` (90), `max_admins` (5), `credential_threshold` (0.8), `tagged_threshold` (0.9), `audit_lookback_days` (30), `vuln_lookback_days` (90), `sla_critical_days` (15), `sla_high_days` (30), `sla_medium_days` (90), `sla_low_days` (180), `expected_asset_count`, and `max_chunks` (50).

## Control coverage

Status semantics: `pass` requires complete, readable evidence with every enabling flag confirmed; `warn` marks partial views, undated items, or minor drift; `fail` marks a verified deficiency; `manual` marks unknown, forbidden, unlicensed, or not applicable evidence and states what a human must collect.

|---|---------|------|---------|-----------|
| 1 | Scan policy configuration | scan_program | TENABLE-01 | Reads `GET /scans`, `GET /editor/scan/templates` (to detect discovery-only templates), `GET /policies`, and `GET /policies/{policy_id}` for every policy a scan references, and judges `settings.safe_checks`, `settings.portscan_range`, and the `plugins` family map: `safe_checks=no` or every family disabled `fail`; a custom port range or more than half of the families disabled `warn`; `pass` when every referenced policy enables safe checks on the default or full port range. Zero scans or discovery-only scans `fail`; a refused details read (needs Standard [32] plus Can View), a policy exposing no settings, a capped details walk (100 policies), or every scan lacking `policy_id` `manual`; some scans lacking `policy_id` cap a pass at `warn`. An unreadable template list disables discovery-only detection and caps the verdict at `warn` with the cause (`scan_templates_in_use`, `policy_templates`, and `discovery_only_scans` render `null`); an unreadable policy list caps at `warn` the same way. |

Every finding carries the FedRAMP, CMMC, SOC 2, CIS, PCI-DSS, DISA STIG, IRAP, and ISMAP mappings from the spec table for that control. Verdicts are additionally capped at `warn` whenever the API key is not confirmed as Administrator, a paginated list returned fewer records than `pagination.total`, was still returning full pages when the page cap was reached (an endpoint that omits `pagination.total` is treated as partial rather than complete in that case), or replayed the same first record on consecutive pages (a stuck offset), an export timed out or downloaded fewer chunks than were available, or any secondary inventory the finding reads is unreadable (the summary names the endpoint and the affected evidence renders `null`). Assessment-level summaries render `null` rather than `0` for the count of any dataset that could not be read.

## Live smoke

```bash
npm --prefix cli run test:tenable:live
```

The script prints a skip message and exits 0 without credentials. With credentials it runs `tenable_check_access` and the scan program assessment against the configured tenant.

## Limitations and manual controls

- Control 1 reads `GET /policies/{policy_id}` (documented `settings` and `plugins` objects) for every policy referenced by a scan, capped at 100 policies per run; the details read needs the Standard [32] role plus Can View on each scan template, and a refused read renders the control `manual`. Performance settings (`max_hosts_per_scan`, `max_checks_per_host`, `thorough_tests`, `report_paranoia`) are recorded as evidence, not judged.
- Report schedules and Lumin exposure metrics have no documented read endpoint; control 19 relies on export job history, which the API returns for completed jobs only within the previous three days, so it is a point-in-time signal rather than proof of a recurring schedule.
- Tenable Security Center controls are `manual` (not applicable) until `TENABLE_SC_URL` is configured; Security Center session token authentication is not implemented.
- Agents that are not licensed render controls 5 and 6 as `manual`.
- Export chunk downloads stop at `max_chunks` (default 50) and the vulnerability export uses `num_assets=5000`; the resulting truncation downgrades verdicts to `warn` and is recorded in `_errors.log`. An export that does not reach FINISHED within the polling deadline is recorded as `TIMEOUT(<last status>)`, treated as unreadable (the dependent controls render `manual`), and its vendor-supplied `reason` is scrubbed like every other error string.
