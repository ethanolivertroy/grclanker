---
title: Palo Alto Networks
description: Read-only security inspection of Prisma Cloud CSPM tenants and PAN-OS firewalls or Panorama with framework-mapped findings and evidence bundles.
---

The Palo Alto Networks integration audits two product surfaces without ever mutating a tenant or a device:

- **Prisma Cloud CSPM** through the REST API (JWT login with an access key): compliance posture, alert rules and open alerts, policies, cloud accounts and account groups, user roles, and tenant integrations (push channels such as Splunk, Amazon SQS, webhooks, and ServiceNow).
- **PAN-OS firewalls and Panorama** through the XML API (`type=op` show commands and `type=config&action=show`): security and decryption rulebases, zones, security profiles, GlobalProtect, administrators, log forwarding, system settings, HA state, and software versions.

Every finding carries the FedRAMP, CMMC 2.0, SOC 2, CIS, PCI-DSS 4.0, DISA STIG, IRAP, and ISMAP references from the compliance mapping table in `specs/paloalto-sec-inspector.spec.md`.

## Setup and authentication

Configure one product or both. When only one product is configured, the other product's controls become `manual` findings that state exactly which evidence a human must collect. The cross-product controls PA-19 (admin roles), PA-20 (logging and SIEM), and PA-21 (data loss prevention) are the exception: each evaluates whichever product is configured and caps at `warn` when only one is, so a single configured product that is compliant renders `warn`, not `manual` and not `pass`. What a non-compliant product renders differs per finding. PA-21 fails when no configured product is compliant, whichever product that is (a Prisma Cloud tenant alone with no enabled data security policy fails, as does a PAN-OS estate alone with no data filtering profile attached to an allow rule), and warns when one of two configured products is compliant. PA-19 and PA-20 fail only on their PAN-OS half (superusers above the threshold or password complexity disabled; rules with `log-end=no` or no syslog or Panorama forwarding), while a non-compliant Prisma Cloud half (System Admin roles above the threshold or zero roles returned; no SIEM integration) warns, so a Prisma Cloud tenant alone never renders worse than `warn` on those two. The `manual` cases are the absence of both products, a failed read of a surface the finding depends on (the partial-view rule under Control coverage), and, for PA-19, zero readable PAN-OS administrators.

### Prisma Cloud

| Variable | Purpose |
|---|---|
| `PRISMA_API_URL` | Regional API URL, for example `https://api2.prismacloud.io` or `https://api.eu.prismacloud.io` (defaults to `https://api.prismacloud.io`). Use the API URL that matches your console URL. |
| `PRISMA_ACCESS_KEY_ID` | Access key ID created under Settings > Access Control > Access Keys. |
| `PRISMA_SECRET_KEY` | Secret key for that access key. |
| `PRISMA_COMPUTE_URL` | Optional Prisma Cloud Compute console path (Compute > Manage > System > Utilities > Path to Console). When unset, the CSPM `GET /meta_info` response field `twistlockUrl` is used; if neither is available, the Compute controls (7 to 11, 24, 25) become manual findings that name this variable. |

The client sends `POST /login` with the access key ID as `username` and the secret key as `password`, then reuses the returned JWT in the `x-redlock-auth` header. Tokens are refreshed by logging in again before the ten-minute expiry, and a `401` triggers one re-login. `429` and `5xx` responses are retried with exponential backoff (honoring `Retry-After`). The access key inherits the permission group of the user who created it; a read-only role such as **Account Group Read Only** or a custom permission group with read access to Compliance, Alerts, Policies, Cloud Accounts, Access Control, and Integrations is sufficient.

#### Prisma Cloud Compute (CWPP)

The Compute console has its own REST API under `/api/v1/`. The client first calls `POST /api/v1/authenticate` with the access key ID and secret key and sends the returned token as `Authorization: Bearer`; when that fails it falls back to the CSPM JWT in `x-redlock-auth`, the alternate method on the PCEE access page. Only System Admin users (mapped to the Compute Administrator role) can call the Compute API. Read endpoints used: `/defenders`, `/policies/runtime/container`, `/policies/compliance/container`, `/policies/compliance/host`, `/policies/vulnerability/images`, `/settings/registry`, `/registry`, `/images`, `/stats/vulnerabilities`, `/stats/compliance`, `/cloud/discovery`, and `/scans`. List endpoints (`/defenders`, `/registry`, `/images`, `/cloud/discovery`, `/scans`) are paged with `limit` and `offset` (50 per page, 500 records per surface). The loop records truncation, with the reason, when the 500-record cap is reached while full pages are still being returned and when the console answers consecutive offsets with the same page (a stuck offset); either caps the dependent findings at `warn` and names the reason in the summary.

### PAN-OS firewalls and Panorama

| Variable | Purpose |
|---|---|
| `PANOS_HOST` | One or more management hostnames or IPs, comma-separated. Panorama is detected automatically from `show system info`. |
| `PANOS_API_KEY` | Pre-generated API key. Sent in the `X-PAN-KEY` header, never in the URL. |
| `PANOS_USERNAME`, `PANOS_PASSWORD` | Alternative to the API key: the client generates one with `type=keygen` (credentials are sent in the POST body). |
| `PANOS_VERIFY_TLS` | Defaults to `true`. Set to `false` only for lab devices with self-signed certificates. The opt-out is scoped to the PAN-OS clients, which then use a `node:https` transport with `rejectUnauthorized: false`; Prisma Cloud requests and every other integration in the process keep certificate verification, and `NODE_TLS_REJECT_UNAUTHORIZED` is never touched. Prefer `NODE_EXTRA_CA_CERTS` with the device CA instead. |

Use a read-only administrator (the built-in `superreader` or a custom admin role with XML API `Configuration` and `Operational Requests` read permissions). Nothing in this integration issues `set`, `edit`, `delete`, or `commit`.

### Optional config file

`PALOALTO_CONFIG_FILE` (or `~/.grclanker/paloalto.json`) may hold the same keys as the environment variables in a flat JSON object. Precedence is explicit tool arguments, then environment variables, then the config file. `PALOALTO_TIMEOUT` (seconds) overrides the 30-second HTTP timeout.

A file named explicitly (the `config_file` argument or `PALOALTO_CONFIG_FILE`) must be readable and parse; the default path is skipped silently when absent. Loader errors use fixed text and never quote the file: a read failure reports `Unable to read Palo Alto config file <path> (<CODE>)` with only the errno code (`ENOENT`, `EACCES`, `EISDIR`), a parse failure reports `Unable to parse Palo Alto config file: invalid JSON in <path> at line N (INVALID_JSON)` with the line derived from the parser's position only, and a file that is not a JSON object reports `INVALID_CONFIG_SHAPE`. Neither the filesystem message nor the `JSON.parse` message (which quotes a window of the source around the failure) is ever interpolated, so an unquoted or misplaced credential in a malformed file cannot leak through the error.

### Redaction and error strings

Configured secrets (`PRISMA_SECRET_KEY`, `PRISMA_ACCESS_KEY_ID`, `PANOS_API_KEY`, `PANOS_PASSWORD`, the key `type=keygen` returns, and the session JWT and Compute token the clients obtain at login) never appear in tool output, findings, `_errors.log`, or bundle files. Every error string is built once and scrubbed at the single sink every collector, access probe, and tool catch block reads through, and redaction runs before any length cap, so a value cut by the cap can never survive as a prefix.

The scrub draws one boundary. A value inside a carrier is replaced with `[REDACTED]` whatever its shape: `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `X-PAN-KEY`, and `x-redlock-auth` header lines, where the value is withheld to the end of the line and a quoted value (in double, single, or JSON-escaped quotes) goes with its quotes whatever the name of the cookie or pair that carries it inside the line; cookie and session assignments; the user-and-secret prefix before the host in a URL; the URL query parameters named `token`, `api_key`, `secret`, and `pass`, and the PAN-OS `key` parameter; the values after the schemes `Bearer`, `Basic`, `Token`, `ApiKey`, and `SSWS`; credential-named assignment pairs in their three spellings (equals sign, colon, and quoted JSON member) and XML attributes (`password`, `secret`, `token`, `api_key`, `secret_key`, `private_key`, `client_secret`, `phash`, `authpwd`, `privpwd`, `snmp-community-string`, `session_id`, and their camelCase forms). A configured secret is replaced wherever it appears, whatever its shape, in its base64, base64url, URL-encoded, and JSON-escaped forms too (four characters or longer). Real token shapes go even when bare in prose: runs of sixteen or more characters with base64 symbols, scattered digits, or token casing, hex digests, PAN-OS API keys (the vendor's fixed six-letter prefix followed by the key body), JWTs, AWS access key ids, and PEM blocks. A bare value shaped like a name (words joined by hyphens or underscores with at most one numeric segment, such as `prod-us-east-2026`, `fw-dc1-01`, or `ethernet1/1`) standing alone in prose is indistinguishable from a resource name and stays, as do titles such as `Basic Network Scan`, count fields such as `"api_keys": 2`, and this integration's own vocabulary (`password-complexity`, `credential-enforcement`, `status_code`). Every bundle file and every tool result passes through the configured-secret pass a final time on its way out, so a key echoed by an upstream body cannot survive even where the general scrub would have left evidence alone. The module's own fixed text crosses that boundary intact: the test suite drives every fixed text emitted on refused, failed, and unconfigured paths (the not-collected markers, the non-JSON and non-XML notes, the Compute discovery reasons, the PAN-OS and Prisma Cloud gate texts, the loader messages) through the scrub and requires it back unchanged.

A 2xx answer that is not the documented document is an unreadable surface, never an empty inventory (the silent-success class). A Prisma Cloud or Compute 200 with an empty body, the HTML page a proxy or SSO portal serves in place of the API, a foreign JSON value, or a JSON object without the documented member (`items`, `policies`, `defenders`, and so on) is described by status, media type, and size only, for example `status 200 with a non-JSON text/html response body (1204 bytes, not echoed) where the documented JSON array was expected`, and recorded with the observed status as a surface that was not read: the probe is not readable, the dataset carries the not-collected marker, and the findings that depend on it render manual or capped, never pass on a missing list. The login answer is held to the same guard: a `POST /login` 200 without the documented `token` member is `status 200 with a JSON response body without the documented "token" member (n bytes, not echoed)`, never a session that silently failed to start. A PAN-OS 200 without a `<response>` element is the non-XML note above and is treated the same way. The guard reaches the records of a list as well: every array surface (alert rules, open alerts, policies, cloud accounts, account groups, user roles, integrations, Defenders, registry scans, images, vulnerability stats, cloud discovery, CI scans) has a documented member set, the identity and status fields its verdicts read, and a 200 array (or one page of a walk) in which no record carries any of them is `status 200 with a JSON array of n records none of which carries any of the documented members "provider", "serviceType", "total", "defended", "err" (n bytes, not echoed)`, an unreadable surface like the shapes above, so `[{"unexpected": true}]` served for cloud discovery leaves PA-24 manual, never pass. A record without any documented member inside an otherwise documented array is unevaluable: it is kept out of the inventory, counted in the collection status (`unevaluable_records`), and named by every finding that reads the surface (`Partial inventory: prisma-compute cloud discovery: 1 of 3 records carry none of the documented members (...) and were not evaluated`, with the count under `unevaluable_records` in the evidence), which caps a pass at warn. The test suite serves every one of the 39 read surfaces (10 Prisma Cloud, 13 Compute, and 8 per PAN-OS device across two devices) an empty 200, an HTML 200 carrying credentials, a foreign JSON object 200, and a foreign JSON array 200 in turn, and requires each to leave a not-collected marker with the observed 200, an unreadable probe, and exactly the verdicts a refusal of the same surface leaves, with nothing of the page in any file; it then serves each of the 13 array surfaces a documented list with one foreign record and requires the record out of the inventory, the count in the collection status, and every dependent verdict capped with the count named.

Response bodies are never echoed. A Prisma Cloud or Compute error with a non-JSON body (an HTML 502 page, an SSO interstitial, a WAF block) is described only as `failed ({status}): non-JSON {content-type} response body ({n} bytes, not echoed)`, whatever content type the server claimed; a JSON body contributes only Prisma Cloud's documented error fields (`message`, `i18nKey`, `error.message`, Compute's `err`, and the `i18nKey`, `message`, or `subject` entries of the `x-redlock-status` header), each scrubbed before it is shortened to 200 characters; a JSON body without those fields is described by length only. A PAN-OS response without a `<response>` element is described as `returned a non-XML {content-type} response (status {n}, {n} bytes, not echoed)`; an XML error contributes only the `<msg>` or `<line>` text and the response `code`, scrubbed before the 300-character cap.

| `paloalto_assess_threat_prevention` | Controls 16 to 18, 21, and 22: antivirus, anti-spyware, vulnerability, WildFire, URL filtering and credential phishing, data loss prevention (Prisma Cloud data policies plus PAN-OS data filtering), and file blocking. |
| `paloalto_assess_device_hardening` | Controls 15, 19, 20, and 23: GlobalProtect, administrators and password complexity (PAN-OS plus Prisma Cloud roles), logging and SIEM forwarding, system hardening, plus supplementary HA state (`PA-HA-01`) and software version (`PA-SW-01`) findings. |
| `paloalto_export_audit_bundle` | Runs everything and writes `core_data/`, `analysis/`, `compliance/`, `QUICK_REFERENCE.md`, `_errors.log` (only on partial failure), and a zip archive under `./export/paloalto` by default. `core_data/` is not a verbatim dump. The PAN-OS configuration is stored with credential-bearing nodes (`phash`, `password`, `secret`, `key` and `pre-shared-key`, `private-key`, `passphrase`, `token`, SNMPv3 `authpwd` and `privpwd`, `snmp-community-string`, and similar names, matched in kebab-case, snake_case, camelCase, and attribute forms) replaced by `[REDACTED]`; settings such as `password-complexity` and `public-key` are kept, and the assessments still evaluate the raw values in memory. The Prisma Cloud and Compute JSON in `core_data/prisma_cloud.json` is redacted as it is collected: every property whose name's last segment denotes a credential (`authToken`, `password`, `clientSecret`, `api_key`, `secret_key`, `private_key`, `credentials`, and similar, in snake_case or camelCase; a bare `key` and `public_key` are kept) is replaced whole, so an integration's `integrationConfig` secrets, a Compute registry credential block, or an image `secrets` list never leak a nested child; `{key, value}` header pairs flagged `secure` or labelled with a credential name lose their `value`; and every remaining string is scrubbed of URL query credentials (the parameters named `token` and `api_key`, among others), the user-and-secret prefix before the host in a URL, Slack, Discord, and Teams token-in-path webhook URLs, and JSON-encoded credential fields. All tools accept the same authentication arguments (`prisma_api_url`, `prisma_access_key_id`, `prisma_secret_key`, `panos_hosts`, `panos_api_key`, `panos_username`, `panos_password`, `config_file`, `verify_tls`, `timeout_seconds`). Tunables: `alert_limit` and `min_compliance_pass_rate` (cloud posture, export) and `max_superusers` (device hardening, export).

## Control coverage

Status semantics: `pass` means the evidence satisfied the check, `warn` means partial evidence or a heuristic concern, `fail` means the evidence contradicted the control, and `manual` means the control cannot be verified through the configured APIs and the summary states the evidence a human must collect.

Verdict-safety rules applied to every finding:

- An unreadable, forbidden (401/403), or errored endpoint or PAN-OS error response yields `manual` with the cause and the evidence to collect, never `pass`.
- Empty inventories never pass by default. Each summary states whether emptiness is treated as `fail` (for example zero alert rules, zero cloud accounts, zero Defenders, zero threat profiles) or `manual` (zero evaluated resources, zero IAM policies, zero security rules, zero zones, zero admins, zero registries, zero cloud discovery entries). The one compliant emptiness is control 5: zero open network exposure alerts passes only when enabled network policies exist and the alert list was read completely.
- Scoped-out, disabled, or unlicensed controls (GlobalProtect not configured, IAM Security not visible, Compute console not reachable) render as `manual`.
- Items without a date (Defenders without `lastModified`, images or registry scans without `scanTime`, CI scans without `time`, devices without `sw-version`) are reported in their own bucket and cap the verdict at `warn`.
- Partial inventories (one device of several unreachable, a truncated alert page, a truncated Compute list) flag the partial view with seen and total counts instead of passing.
- Enabling flags are read explicitly: `enabled=true`, `connected=true`, `disabled!=true`, `log-end=yes`, HA `enabled=yes`. An absent or false flag never supports `pass`; an implicit `log-end` default is reported separately and caps at `warn`.
- Alert pagination follows `nextPageToken` to completion. The loop records truncation, with the reason, when `alert_limit` is reached while a token remains, when a page is empty but still carries a token, when a token repeats (a stuck cursor), or when `totalRows` exceeds what was read; Compute lists record truncation at the 500-record cap or on a stuck offset. Truncation caps PA-02, PA-03, PA-05, PA-06 (alerts) and the Compute findings that read the truncated list at `warn`, and the summary and `partial_inventory` evidence name the reason.
- A finding that reads several surfaces never passes on a partial view. When any surface it reads is unreadable (`GET /v2/alert` for PA-02, PA-03, PA-05, and PA-06, `GET /cloud/group` for PA-04, `GET /defenders` for PA-08 and PA-09, `GET /images` and `GET /stats/vulnerabilities` for PA-07, `GET /registry` for PA-11, `/config/shared` for PA-15's authentication profiles, `GET /user/role` and the `/mgt-config` device tree for PA-19, the Prisma Cloud integration list for PA-20, and the policy rulebases for PA-21), the finding is `manual`, the summary starts with `Evidence unavailable (...)`, and `unreadable_sources` names each failed read.
- Evidence derived from an unreadable surface renders `null`, never `0` or an empty list: `accounts: null` means the account list was not read, `accounts: 0` means it was read and is empty. The collection status block of each assessment summary follows the same rule (`cloud_accounts`, `open_alerts_sampled`, and `open_alerts_truncated` render `null` when their surface failed, and `unreadable_surfaces` and `truncated_surfaces` name the reads that did not complete).
- A surface that was refused, failed, or never reached is never written as an empty list or `null`. Its place in `core_data/prisma_cloud.json` and in the per-device PAN-OS snapshot holds a marker, `{ "collected": false, "status": <observed HTTP status or null>, "dataset_status": "forbidden" | "not_found" | "error" | "unavailable", "endpoint": "GET /...", "error": "<scrubbed message>" }` (an unreachable Compute console writes an `unavailable` marker naming the `GET /meta_info` request that could not resolve it), and each assessment summary carries a `collection` object with one entry per surface (`status`, `endpoint`, `http_status`, `seen`, `truncated`, `error`; the PAN-OS block is keyed by device host). `truncated` is derived from the observed walk (a token still present after the alert limit, an empty page or a repeated token, `totalRows` above the records read, the Compute record cap, a stuck offset), never from a default, and `seen` and `truncated` render `null` for a surface that was not read. Every endpoint or status code named anywhere in a finding, summary, tool result, or `_errors.log` line is the request that was actually made (method and path taken from the thrown error) and the status it actually returned; a transport failure records a `null` status.
- Export reruns allocate a new directory and derive the zip name from it, so a prior bundle is never overwritten.

## Live smoke test

```bash
npm --prefix cli run test:paloalto:live
```

The script exits 0 with a skip message when neither product is configured. Otherwise it runs `paloalto_check_access` and one assessment (cloud posture when Prisma Cloud is configured, firewall policy otherwise).

## Limitations

- Prisma Cloud Compute (CWPP) controls 7 to 11 and 24 are automated when the console is reachable. Control 25 caps at `warn`: CI scan results come from the documented `GET /scans` endpoint, but no admission control (OPA) read endpoint could be located on the public pan.dev CWPP reference, so admission rules remain a manual review. The CSPM `GET /meta_info` page is also not published on pan.dev; the PCEE access guide documents copying the console path from the UI, which is what `PRISMA_COMPUTE_URL` carries.
- Control 3 uses the tenant's IAM policies and open `iam` alerts as the overprivilege signal. The documented `POST /api/v1/permission` endpoint runs a caller-supplied IAM RQL query and returns raw permission rows, which would require this tool to hard-code its own RQL definition of "overprivileged" that cannot be validated without a licensed CIEM tenant; the built-in IAM policies already encode those detections. `GET /api/v1/permission/alert/search` only returns the RQL behind one alert ID.
- Control 2 reads alert rules from `GET /v2/alert/rule`. `GET /alert/policy` (List Alert Counts By Policy) is documented but only returns open alert counts grouped by policy, not rule configuration.
- Control 20 reads push integrations from `GET /api/v1/tenant/{prismaId}/integration` with the `prismaId` from the login response; `GET /integration` only lists Okta, Qualys, and Tenable pull integrations and is used as a fallback when no `prismaId` is returned.
- Shadow detection is heuristic: a rule is reported as shadowed when an earlier enabled rule in the same rulebase already allows any source, destination, and application for the same zones.
- Software version evaluation flags PAN-OS 9.x and older and missing content versions; end-of-life dates for current releases must be checked against the Palo Alto Networks end-of-life summary.
- WildFire cloud connectivity, GlobalProtect HIP requirements, admin MFA enforcement, and log retention are reported as review items inside the finding summaries.
- Disabling TLS verification affects only the PAN-OS clients created for that run (a dedicated `node:https` transport). The process-wide `NODE_TLS_REJECT_UNAUTHORIZED` variable is never set.
