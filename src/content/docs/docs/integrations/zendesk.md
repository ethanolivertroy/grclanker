---
title: Zendesk
description: Read-only Zendesk Support security inspection covering authentication, access control, audit logging, data protection, apps, brands, and external integrations, with an exportable audit bundle.
---

The Zendesk integration inspects a Zendesk Support account through the public Support API and renders the 25 controls from `specs/zendesk-sec-inspector.spec.md` as normalized findings. Every tool is read-only: nothing is created, updated, or deleted in the account.

## What it inspects

- Authentication: SSO enforcement, account-level two-factor enforcement plus per-agent enrollment, team member password policy, IP restrictions, session expiration, and end-user sign-in methods, all read from the admin-only [Security Settings](https://developer.zendesk.com/api-reference/ticketing/account-configuration/security_settings/) endpoint and the documented per-user `two_factor_auth_enabled` flag.
- Access control: custom roles that grant admin-equivalent permissions, admin count and dormant admins, group segmentation, API token exposure with token creation and deletion events enumerated from the audit log, and OAuth client scope, redirect URI, and token hygiene.
- Data protection: audit log availability and retention (Enterprise), the HIPAA evidence prompt, active deletion schedules by object, authenticated attachment downloads, attachment limits, and suspended ticket backlog age.
- Integrations: marketplace and private app inventories, sandbox provisioning, cross-brand help center consistency, sharing agreements, https-only targets and webhooks, and triggers or automations that deliver ticket data to external destinations.

## Setup and authentication

Zendesk retired email and password access to the API, so the tools support two credential types:

| Mode | How it is sent | When to use |
|------|----------------|-------------|
| API token | `Authorization: Basic` carrying the base64 encoding of the email address, the literal `/token:` separator, and the API token | Quickest to set up. Zendesk is retiring API tokens (unused tokens are deactivated from July 28, 2026 and all API tokens stop working on April 30, 2027), so plan the OAuth migration. |
| OAuth access token | `Authorization: Bearer {token}` | Preferred. Create an OAuth client in Admin Center, grant the `read` scope, and mint an access token. |

Create an API token in Admin Center under Apps and integrations > APIs > Zendesk API (API token access must be enabled). Use an **admin** identity: several surfaces (security settings, deletion schedules, OAuth clients and tokens, audit logs, owned apps, brands, suspended tickets) are admin-only, and the assessors cap every verdict at `warn` when the credential is not an admin because a lower role sees only a partial view of the account. The audit log and custom roles additionally require an Enterprise plan.

Configuration precedence is explicit tool arguments, then environment variables, then a JSON config file:

| Environment variable | Purpose |
|----------------------|---------|
| `ZENDESK_SUBDOMAIN` | The `{subdomain}` in `https://{subdomain}.zendesk.com` (a full URL is accepted). |
| `ZENDESK_EMAIL` | Email that owns the API token (API token mode only). |
| `ZENDESK_API_TOKEN` | API token (API token mode). |
| `ZENDESK_OAUTH_TOKEN` or `ZENDESK_ACCESS_TOKEN` | OAuth access token (bearer mode). When both an OAuth token and an API token are present, OAuth wins unless `email` and `api_token` are passed explicitly. |
| `ZENDESK_BASE_URL` | Optional API base override. Defaults to `https://{subdomain}.zendesk.com/api/v2`. |
| `ZENDESK_TIMEOUT` | Optional HTTP timeout in seconds. Defaults to 30. |
| `ZENDESK_CONFIG_FILE` | Optional path to a JSON config file. Defaults to `~/.zendesk/config.json`. |

The config file accepts `subdomain`, `email`, `api_token`, `oauth_token`, `base_url`, and `timeout_seconds`:

```json
{
  "subdomain": "acme",
  "oauth_token": "your-oauth-access-token"
}
```

A file named explicitly (the `config_file` argument or `ZENDESK_CONFIG_FILE`) must be readable and parse; the default path is skipped silently when absent, and an empty file contributes no settings. Loader errors use fixed text and never quote the file: a read failure reports `Unable to read Zendesk config file <path> (<CODE>)` with only the errno code (`ENOENT`, `EACCES`, `EISDIR`), a parse failure reports `Unable to parse Zendesk config file: invalid JSON in <path> at line N (INVALID_JSON)` with the line derived from the parser's position only, and a file that is not a JSON object reports `INVALID_CONFIG_SHAPE`. Neither the filesystem message nor the `JSON.parse` message (which quotes a window of the source around the failure) is ever interpolated, so an unquoted or misplaced token in a malformed file cannot leak through the error.

Tokens never appear in tool output, bundle files, or error messages; the client redacts them before surfacing any failure. A configured `ZENDESK_BASE_URL` is reduced at configuration to its scheme, host, port, and path: a user-and-secret prefix, query, or fragment is dropped before the first request, so it never leaves in a request URL, never enters the configured origin a next link is compared against, and never reaches an output (the guide, summaries, and metadata name the subdomain, not the URL); the test suite configures the base URL with a user-and-secret prefix and requires every request, tool result, bundle file, and zip entry free of it. Credential-bearing properties inside API records are redacted the same way before a snapshot is kept: `token`, `full_token`, and `refresh_token` on `/oauth/tokens` records, `secret` on OAuth clients, `password` and `token` on legacy targets, webhook `authentication.data` values, `custom_headers` values, and signing secrets, and `api_key`, `password`, or `token` values in app installation settings are replaced with `[REDACTED]`. Property names are matched on their last segment after splitting `snake_case`, `camelCase`, and header spellings, so `apiKey`, `clientSecret`, `refreshToken`, `accessToken`, `secretKey`, `passphrase`, `Authorization`, `X-Api-Key`, and `X-Auth-Token` are covered too, while ids, scopes, client ids, expiry and creation dates, usernames, header names, `public_key`, and a bare `key` are kept for the assessments. String and numeric values under those names are replaced; a `{name, value}` pair whose `name` is a credential in either the walker's vocabulary (an owned app parameter named `api_token`) or the error-text rules' (a header named `x-redlock-auth`, `X-Auth`, or `Cookie`), whatever its `secure` flag says, and any parameter flagged `secure: true` lose their `value`, `default`, and `default_value` fields while the name and kind stay; a benign pair flagged `secure: false` (`X-Trace`, `region`) keeps its value.

Credentials carried inside other string values are scrubbed too, in every string a snapshot keeps: URL query parameters named `token`, `api_key`, `client_secret`, `access_token`, `signature`, or `sig` in `target_url`, `endpoint`, `redirect_uri`, or `url` values keep their name and lose their value to `[REDACTED]`, with the scheme, host, path, and other parameters kept; the user-and-secret prefix before the host in a URL is replaced whole by `[REDACTED]`, so only the scheme and host remain; Slack, Discord, and Microsoft Teams incoming-webhook URLs whose path is the secret keep only the service prefix; and credential fields inside JSON encoded as a string (an app setting holding `{"token":"..."}`) are replaced in place. The redacted copy is what the assessments read, so ZD-24 and ZD-25 still see the scheme and host of every destination.

A 2xx answer that is not the documented JSON document is an unreadable surface, never an empty inventory (the silent-success class). A 200 with an empty body, the HTML page a proxy or captive portal serves in place of the API, a foreign JSON value, or a JSON object without the documented member (`users`, `webhooks`, `oauth_tokens`, `settings`, and so on) is described by status, media type, and size only, for example `200 OK with a JSON response body without the documented "users" array (2 bytes, not echoed)`, and recorded with the observed status as a surface that was not read: the access probe is not readable, the dataset carries the not-collected marker, and the findings that depend on it render manual or capped, never pass on a missing list or read a missing setting as disabled.

Error strings follow the same discipline at the single place they are built and again at every sink. A non-2xx response with a non-JSON body (an HTML proxy page, an SSO interstitial, a rate-limit page) is described only as `{status} {statusText}; non-JSON {content-type} response body ({n} bytes, not echoed)`, whatever content type the server claimed; a JSON body contributes only Zendesk's documented error fields (`error`, `description`, `message`, `error.title`, `error.message`, `errors[].title` or `detail`), each scrubbed before it is shortened to 200 characters so a cut can never leave the head of a secret behind. The `ZendeskApiError` constructor, the transport-failure path, the snapshot layer that feeds every finding and `core_data/` file, and the tool catch blocks all apply the same unanchored pass, so a message assembled at a throw site cannot carry a credential into a finding, summary, `_errors.log`, or the bundle.

That pass draws one boundary. A value inside a carrier is replaced with `[REDACTED]` whatever its shape: `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, and similar header lines, each by its class: an `Authorization` or `Proxy-Authorization` value keeps its scheme word as spelled (`Bearer`, `Basic`, `Digest`, and the other schemes listed below, in any casing) and loses the one token, or the one quoted string, after it, so the operator still reads which scheme was replayed and prose after the token stays, while a parameter list after the scheme (`Digest username=..., realm=...`, `AWS4-HMAC-SHA256 Credential=...`) and a value that opens with anything but a listed scheme word (`GenieKey <token>`, `SharedKey <account>:<signature>`, `Bot <token>`, a bare token) goes whole to the end of the line, since an unknown first word may be a scheme with its credentials after it; a `Cookie`, `Set-Cookie`, or `X-Cookie` line is a list of pairs and goes whole to the end of the line, so cookie attributes such as `Path` and `Expires` go with the cookie; every other header (`X-Api-Key`, `X-Auth-Token`, `X-Vault-Token`, and the like) carries one token and loses its first token, so a JSON fragment or prose after it on the same line is still read, or, when its value opens with a listed scheme word (`X-Auth-Token: Bearer <token>`), loses the word and the token after it together under one marker. In every class a quoted value (in double, single, or JSON-escaped quotes) ends at its closing quote and goes with its quotes whatever the name of the cookie or pair that carries it, even when a `; Name:` sits inside the quotes, and a whole-line value ends at the `;` or `,` before the name of the next header on a compound line (several headers separated by `;` or `,`; a following header name may hold dots), at a line break the stringify left escaped (`\n`, `\r`, `\u000a`), or else at the end of the line, so a quoted value that nothing closes ends as an unquoted one does, the next header keeps its name and gets its own treatment, and a `Content-Type` or `Date` after a cookie keeps its name and value; a single-token header value, the token after a scheme word, an equals-sign pair value, and a `--flag` value end at whitespace or at any control character the stringify left escaped (`\t`, `\b`, `\f`, `\v`, `\0`, `\u0009` and the other `\u00XX` control codes, `\x09`), as they do at the raw character, so a credential pair chained after such an escape (`api_key=<value>\tpassword: <value>`) is read on its own and loses its own value, and a count under a plural credential word ends there too (`keys: 3\tcookies: 0` stays); quotes escaped to any depth (`\"` one level down, `\\\"` two) are read at their own depth, so a header pair, credential pair, quoted attribute, or quoted assignment inside a JSON body that was stringified into a string value loses its value and keeps its escaped quotes; a header name or pair key is read the same right after such an escape (`\nAuthorization: Bearer <value>`, `\tapi_key=<value>`) as at a word boundary; a quote inside a token is content of the value it sits in, in a header value, pair value, quoted attribute, or URL query value alike (RFC 6265 lets a cookie name or value carry an apostrophe, so `sid=O'<value>` and a pair named `my'pref` go with their cookie), and only a quote at the end of a token, or one after `=` with nothing but a delimiter or the end behind it (a base64 value ending in `=`), closes the text the line was quoted in, so the closing quote and the following members of an enclosing JSON string survive; a header line is read before the URL query rule, so a cookie pair whose name holds `&` or `#` goes with its cookie, and a bare query value never takes a backslash, so `?token=<value>\"` keeps the escaped quote and `?api_key=<value>\nstatus 502` keeps the text after the line break; cookie and session assignments (the `_zendesk_session` cookie among them); the user-and-secret prefix before the host in a URL, bare or with its slashes escaped by a stringify (`https:\/\/user:secret@host`), which ends where the authority does, at the first `/`, `?`, or `#`, so an `@` inside a query or fragment (`https://h?e=a@x.com&token=<value>`, `https://h#f@x.com`) is not such a prefix, the host `h` stays, the query is read pair by pair (`&token=` loses its value), and a `webhook_url` holding that URL reduces to `https://h/[REDACTED]`; the URL query parameters named `token`, `api_key`, `client_secret`, `access_token`, `signature`, and `pass`; the path and query of a URL under a `webhook` or `webhook_url` key, whose origin stays; the values after the schemes `Bearer`, `Basic`, `Digest`, `Token`, `OAuth`, `Negotiate`, `NTLM`, `SSWS`, `ApiKey`, `Splunk`, `Snowflake`, and `AWS4-HMAC-SHA256` in any casing, where the scheme word itself stays and only a listed prose word after it (`Basic authentication`), an auth-param name (`Bearer realm=`), or, after the nouns `Token`, `OAuth`, `Splunk`, and `Snowflake`, a short plain lowercase word (`Token expired`) is read as prose and stays; credential-named assignment pairs in their three spellings (equals sign, colon, and quoted JSON member), wherever the key starts (at a word boundary, after `--`, after a Java `-D`, or after a path slash) and as `--key value` flags (whose name may open with a letter or an underscore, so `--_zendesk_session <value>` is one), with `secret_id`, bearer ids such as `token_id`, and `connection_string` among the credential names, while a colon-terminated credential-named key that ends a path segment is a label whose value is at most one token: a singular label (`/etc/app/password: <value> was rejected`, `vault read secret/app/token: <value> has no policy`) takes that token whatever its shape, a random string or a plain word, and whatever follows it, so the text renders `/etc/app/password: [REDACTED] was rejected`, while a plural label names a collection (`GET /api/v2/oauth/tokens: request failed`, `/api/v1/api-tokens: request failed with 403`), so prose continuing after the token means there was no value and the text stays, and a lone token after a plural label is removed; and XML attributes. A scheme word that starts the value of a credential-named key other than `Authorization` (`api_key: Bearer <value>`) is part of the value and goes with it. A configured secret (the API token, the OAuth token, and the base64 `{email}/token:{api_token}` value the Basic header carries, four characters or longer) is replaced wherever it appears, whatever its shape, in its base64, base64url, URL-encoded, and JSON-escaped forms too. Real token shapes go even when bare in prose: runs of sixteen or more characters with base64 symbols, scattered digits, or token casing, hex digests, JWTs, AWS access key ids, GitHub, Stripe, and Slack prefixed tokens, and PEM blocks. A bare value shaped like a name (words joined by hyphens or underscores with at most one numeric segment, such as `prod-us-east-2026` or `acme-support-01`) standing alone in prose is indistinguishable from a resource name and stays, as do titles such as `Basic Support Plan`, this integration's own vocabulary (`api_token_access`, `password_policy`, `status_code`), and one value under a credential-named key: a count, that is a bare integer (digits alone, or digits followed by a space, as in `oauth_tokens: 1 active`) under a key whose last word is one of the plural words `tokens`, `secrets`, `keys`, `cookies`, `passwords`, or `credentials`, in the JSON member spelling (`"oauth_tokens": 1`, `"oauth_tokens": "1"`), the colon spelling (`oauth_tokens: 1`), and the equals spelling (`oauth_tokens=1`). A singular key keeps the rule (`pin: 1234` and `password=7` lose their values), and so does any other value under a plural key (`tokens: rotate them` loses its value). Every bundle file and every tool result passes through the configured-secret pass a final time on its way out, so a token echoed by an upstream body cannot survive even where the general scrub would have left evidence alone. The module's own fixed text is worded to cross that boundary intact: an `_errors.log` line reads `oauth_tokens dataset: <error>`, never `oauth_tokens: <error>`, which the pair rule would read as a credential and replace, and the test suite drives every fixed text the module emits on refused, unavailable, failed, and silent-success paths through the scrub and requires it back unchanged.

A snapshot that was refused, not on the plan, or failed is never written as an empty list or `null`. Its `core_data/` file holds a marker in its place, `{ "collected": false, "status": <observed HTTP status or null>, "dataset_status": "forbidden" | "not_found" | "error", "endpoint": "GET /api/v2/...", "error": "<scrubbed message>" }`, and every assessment summary carries a `collection` object with one entry per snapshot it read (`status`, `endpoint`, `http_status`, `seen`, `truncated`, `truncation_reason`, `pages`, `error`). `truncated` is derived from the observed page walk (the reasons listed under the tools below), never from a default, `truncation_reason` names why paging stopped and is `null` for a list read to completion, `seen`, `truncated`, and `pages` render `null` for a snapshot that was not read, and `seen` renders `null` for a truncated list that delivered no item (`0` would read as an empty inventory). Every endpoint or status code named anywhere in a finding, summary, tool result, or `_errors.log` line is the request that actually failed (its method and path are taken from the thrown error) and the status it actually returned.

## Tools

| Tool | Purpose |
|------|---------|
| `zendesk_check_access` | Probes 20 read surfaces (current user, account settings, security settings, team members, custom roles, groups, group memberships, audit logs, OAuth clients and tokens, app installations, owned apps, brands, webhooks, targets, triggers, automations, sharing agreements, deletion schedules, suspended tickets) and reports which admin-only or Enterprise-only surfaces the credential cannot read. |
| `zendesk_assess_authentication` | Controls 1-5 and 21. |
| `zendesk_assess_access_control` | Controls 6-8, 13, and 14. |
| `zendesk_assess_data_protection` | Controls 9-12 and 18-20. |
| `zendesk_assess_integrations` | Controls 15-17 and 22-25. |
| `zendesk_export_audit_bundle` | Runs the access check and all four assessments, then writes `core_data/` (the redacted API snapshots the assessments read, never the raw responses), `analysis/` (`findings.json` and one JSON per category), `compliance/` (`executive_summary.md`, `unified_compliance_matrix.md`, and one report per framework), `QUICK_REFERENCE.md`, `_errors.log` when collection was partial (one scrubbed error string per failed snapshot, carrying the HTTP status and Zendesk's documented error fields only, and one partial-inventory line per list that stopped paging early, naming the reason), and a paired `.zip`. Reruns allocate a new directory (`-2`, `-3`, ...) and the zip name follows the directory, so a prior bundle is never overwritten. |

Assessment tools accept `admin_threshold` (default 5), `stale_days` (default 90), `retention_days` (default 365), `session_timeout_minutes` (default 480, the longest acceptable team member inactivity timeout), `suspended_ticket_age_days` (default 30), and `max_items` (default 2000, the point at which an inventory is recorded as truncated). Cursor-paginated lists follow `links.next` until `meta.has_more` is false (Users and Groups also request `include_boundary_indicators=true`), offset-paginated lists follow `next_page` until it is null or a page comes back short, and when a full page omits `next_page` the client requests the next numeric page (`page` incremented by one) rather than treating the omission as the end (the cursor rule is unchanged); a list is recorded as truncated whenever it stops for any reason other than the server's end marker: `max_items`, the 100-page cap, an empty or fully repeated page returned while `has_more` is true or a `next_page` URL is present, a cursor or `next_page` that points back at the page just fetched, or a next link the client refused to follow. A server-supplied `links.next` or `next_page` is followed only on the configured origin: before any request is built for it, an absolute link (one naming a scheme, `https:` and `javascript:` alike, or opening with two slashes or two backslashes, which a URL parser reads as protocol-relative) is resolved against the configured base URL and must match its scheme, host, and port exactly and carry no user credentials (a relative link is a path on the base URL); otherwise the credential never leaves for it, the pages already read are kept, and the list stops as truncated with a fixed-text reason that names only the rejected origin (its scheme, host, and port, or the bare scheme of a `javascript:`, `data:`, `blob:`, or `file:` link without a host) and the configured origin, never the link's path, query, or credentials. Every truncated list carries its reason as `truncation_reason` (in the list result, the `collection` entry, and `core_data/`), the access check reports it as `truncationReason` on the probe and in a note, the finding summaries quote it in their truncation sentence, and `_errors.log` gets one `<name> dataset: partial inventory, paging stopped early because ...` line per list that stopped early. A truncated inventory downgrades every verdict that depends on it, and the access check marks a probe count that hit its sample cap with a trailing `+`. The export tool adds `output_dir` (default `./export/zendesk`); output paths are resolved inside that root with traversal and symlinked-parent protection.

Every finding has the shape `{id, control, title, severity, status, summary, evidence, mappings}`. Severity is one of `critical | high | medium | low | info`, and status is one of:

- `pass`: verified from documented API fields, read to completion, by an admin credential.
- `warn`: verified but needs review, or the evidence was partial (truncated inventory, undated items, non-admin credential).
- `fail`: a verified gap.
- `manual`: the API does not expose the setting, the endpoint was forbidden or unavailable on the plan, or the inventory was suspiciously empty. The summary names the cause and the exact Admin Center evidence a reviewer must collect. Manual never counts as passing.

## Framework mappings

Every finding carries the row from the spec's compliance table for its control, prefixed by framework (`FedRAMP`, `CMMC`, `SOC 2`, `CIS`, `PCI-DSS`, `DISA STIG`, `IRAP`, `ISMAP`). The export bundle renders one report per framework under `compliance/`, filtering each finding's mappings to that framework. For example, control 2 maps to `FedRAMP IA-2(1)`, `CMMC IA.L2-3.5.3`, `SOC 2 CC6.1`, `CIS 4.5`, `PCI-DSS 8.3.2`, `DISA STIG SRG-APP-000149`, `IRAP ISM-1401`, and `ISMAP 8.2.2`.

## Live smoke

Export `ZENDESK_API_TOKEN` from your secrets manager first (the value is never shown here), then run:

```bash
ZENDESK_SUBDOMAIN=acme ZENDESK_EMAIL=admin@example.com \
  npm --prefix cli run test:zendesk:live
```

The script prints a skip message and exits 0 when no credentials are present. With credentials it runs `zendesk_check_access` and `zendesk_assess_access_control` and prints the per-surface access status and each finding.

## Limitations and manual controls

- Controls 11 and 19 are always `manual`: neither the [Account Settings](https://developer.zendesk.com/api-reference/ticketing/account-configuration/account_settings/) nor the [Security Settings](https://developer.zendesk.com/api-reference/ticketing/account-configuration/security_settings/) reference publishes a HIPAA or Advanced Data Privacy field or an allowed attachment file type list. Each finding names the Admin Center page to capture.
- Controls 1, 3, 4, 5, 12, and 21 are verified from the Security Settings and Deletion Schedules endpoints and render `manual` only when those admin-only endpoints are forbidden. The "Anybody can submit tickets" portion of control 21 stays manual because neither reference publishes it.
- Controls 13, 15, 16, and 23 are `manual` whenever the inventory is non-empty: reviewing token ownership, app permissions, or sharing partners is a human activity. The finding carries the inventory as evidence.
- The API token inventory endpoint is not part of the published API reference and is not called; token creation and deletion events are reconstructed from the audit log (`filter[source_type]=apitoken`), which needs an Enterprise plan and cannot prove that zero tokens exist.
- Audit logs and custom roles require an Enterprise plan; the tools report 403 or 404 as `manual` with a plan or permission cause, never as a pass.
- Help Center article visibility, Talk, Chat, and Sell settings are not inspected.
- Non-admin credentials cap every verdict at `warn`.
- A finding that reads several inventories never passes on a partial view: when a secondary inventory it needs (Account Settings for ZD-12 and ZD-21, custom roles for ZD-12, the token audit log for ZD-13, OAuth tokens for ZD-14, owned apps for ZD-15, targets or webhooks for ZD-24 and ZD-25) is unreadable or truncated, the verdict is capped at `warn` with the cause named and `verdict_capped_by_unreadable` listed in evidence. Counts and lists derived from an inventory that could not be read render as `null` in finding evidence and assessment summaries, never `0` or `[]`.
- A truncated list is an incomplete inventory, and a verdict over it says only what the seen population supports. A count over a truncated list is a lower bound: a positive count renders as observed, qualified by `inventory_truncated` and the summary's truncation sentence, and a count of zero renders `null` rather than `0`, because the unread remainder may hold what the seen records did not. Item-level detail (member names and emails, admin and token lists, app titles, destination hosts) is withheld as `null` while the list is truncated, with the lower bound beside it under a `_count` key, so a partial list is never filed as the review list; the summary says how many items were seen and that the detail is withheld until the inventory is read to completion (a higher `max_items`, a fixed cursor, or the missing permission restores it). No finding passes over a truncated inventory it read, and a `fail` that rests on the absence of records (zero seen) is `warn` while the list that found none was truncated. The `pass`, `warn`, `fail`, and `manual` counts of a category summary follow the same rule: when an inventory the category's findings read was unreadable or truncated, a count of zero renders `null`, and the executive summary renders it as `none seen (not asserted: an inventory the findings read was incomplete)`. The 100-entry audit log sample ZD-09 reads stops at its cap by design and is complete when it filled; a sample cut short before that (a stalled cursor or a refused next link) is a truncated list like any other, so ZD-09 renders `warn` with `sample_cut_short: true` and `actions_seen` withheld, and a read that stopped before any entry arrived is `manual` rather than a verified empty log.
